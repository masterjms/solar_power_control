# 태양광 가로등 통합 관제 서버

LTE 모뎀이 달린 태양광 가로등과 난간 LED 조명 1만 대를 한 화면에서 보고, 끄고 켜고, 설정을 바꾸고, 펌웨어까지 원격으로 갱신하는 관제 서버입니다.
단말 펌웨어 개발자 1명과 서버 개발자 1명이 2026년 9월 25일부터 함께 만들었고, 이 저장소는 서버 쪽 전체입니다.
백엔드, 데이터베이스, MQTT 브로커, 관리 화면, 인프라, 시험 도구, 설계 문서가 모두 들어 있습니다.

---

## 1. 개발 배경

골목길과 산책로에 설치되는 태양광 가로등은 전기 공사 없이 낮에 충전하고 밤에 스스로 켜집니다.
그런데 설치 대수가 늘어나면 문제가 생깁니다.
배터리가 약해진 등, 고장 난 등, 통신이 끊긴 등을 사람이 돌아다니며 찾아야 했고, 점등 시각이나 밝기를 바꾸려면 현장에서 단말을 직접 만져야 했습니다.

이 프로젝트의 목표는 다음과 같았습니다.

- 지자체 단위로 수천에서 1만 대까지의 가로등을 한 서버로 관제합니다.
- 단말은 STM32 마이크로컨트롤러와 WD-N522S LTE Cat.M1 모뎀으로 이루어진 저전력 장비이므로, 모뎀이 할 수 있는 일의 한계 안에서 프로토콜을 설계합니다.
- 24시간 멈추지 않는 서버를 목표로, 재접속 폭주와 DB 장애와 브로커 재시작을 처음부터 시험 항목에 넣습니다.
- 클라우드에 묶이지 않고 공공기관이 직접 계약한 국내 클라우드나 자체 서버에도 그대로 설치해 넘길 수 있게 만듭니다.

## 4. 시스템 구조

```text
 태양광 가로등 1만 대                       관리자 브라우저
 STM32 + LTE Cat.M1 모뎀                         │ HTTPS
        │ MQTT over TLS 8883                     ▼
        ▼                                  ┌───────────┐
 ┌──────────────┐                          │   nginx   │  로그인 확인, 보안 헤더,
 │  Mosquitto   │                          │           │  관리자 IP 제한
 │  + go-auth   │                          └─────┬─────┘
 └──────┬───────┘                                │
        │ 구독·발행, 인증 질의, 접속 로그            ▼
        └──────────────────────────────▶ ┌──────────────┐      ┌──────────────┐
                                         │   FastAPI    │ ───▶ │  PostgreSQL  │
         단말 OTA 다운로드 ─────────────▶ │ 단일 프로세스 │      │   월 파티션   │
         Range 요청                        └──────────────┘      └──────────────┘
```

- 단말과 서버는 MQTT로만 이야기하고, 펌웨어 파일만 HTTPS로 받습니다.
- 백엔드는 하나의 프로세스 안에서 MQTT 수신, REST API, 주기 작업을 모두 돌립니다.
- 브로커는 단말 인증과 토픽 권한을 백엔드에 물어보고, 백엔드는 브로커의 접속 로그를 읽어 단말의 온라인 여부를 판단합니다.

## 5. 대규모 트래픽을 어떻게 풀었는가

목표 규모는 단말 1만 대, 이력 1년 보관이었습니다.
먼저 숫자를 계산했습니다. 1만 대가 10분마다 상태를 보내면 초당 17건이고, 1분 주기로 줄여도 초당 167건입니다.
평상시 처리량은 단일 프로세스로 충분했습니다. 진짜 위험은 평균이 아니라 순간이라고 판단했고, 아래 항목을 집중해서 설계했습니다.

### 5.1 재접속 폭주

브로커가 재시작되거나 통신사 망이 잠깐 끊기면 1만 대가 30초 안에 한꺼번에 다시 접속합니다.
접속마다 서버가 응답 메시지를 바로 쏘면 서버와 브로커와 모뎀이 함께 무너집니다.

- 서버 응답은 토큰 버킷으로 초당 상한을 두고 대기열로 내보냅니다. 대기열에도 상한을 두어 넘치면 가장 오래된 것을 버리고, 버린 단말은 다음 상태 보고 때 설정 번호 비교로 다시 잡히게 했습니다.
- 단말의 승인 상태와 지역 그룹은 retain 메시지 하나에 담아 브로커에 보관합니다. 다시 접속한 단말은 서버를 거치지 않고 브로커에서 바로 자기 상태를 받으므로, 서버가 바빠도 단말은 정상 운전을 이어 갑니다.
- 명령 토픽에는 절대 retain을 걸지 않습니다. 재접속한 단말에 지난 소등 명령이 되살아나는 사고를 막기 위해서입니다.
- 단말 인증은 브로커 플러그인이 백엔드에 묻는 구조인데, 인증과 권한 결과를 600초 동안 캐시해 1만 대 재접속이 1만 번의 HTTP 호출로 이어지지 않게 했습니다.

### 5.2 상태 보고 저장

- 상태 보고를 받을 때마다 트랜잭션을 열지 않고 1초 동안 모아서 한 번에 씁니다. 단말이 몇 대든 초당 트랜잭션은 1개입니다.
- 단말별 최신값은 단말 UUID를 키로 한 버퍼에 두어 단말 수 이상으로 커지지 않습니다.
- DB가 잠깐 멈추면 이력을 무한히 쌓아 두지 않고 버린 뒤 그 수를 셉니다. 메모리가 차서 서버 전체가 죽는 것보다 이력 일부를 잃는 쪽을 택했고, 버린 건수는 서버 상태 화면에 바로 보이게 했습니다.

### 5.3 1년 이력과 디스크

1만 대의 10분 보고는 하루 144만 행, 1년이면 약 5억 행입니다.
실측으로 한 행이 색인 포함 약 650바이트임을 확인하고, 13개월 보관 시 약 360GB가 필요하다고 계산했습니다.

- 상태 보고 표를 월 단위 네이티브 파티션으로 나누고, 보관 기간이 지나면 행을 하나씩 지우지 않고 파티션을 통째로 버립니다. 1년치를 정리해도 DB에 부담이 없습니다.
- 그래프와 통계는 원본이 아닌 단말·날짜별 하루 요약 표를 읽습니다. 하루 요약은 1만 대 10년이어도 약 6GB라 영구 보관합니다.
- 보관 기간은 운영자가 서버 설정 화면에서 1개월에서 13개월 사이로 정합니다.

### 5.4 그룹 명령과 대량 작업

- 법정동 하나에 명령을 보낼 때 단말 수만큼 메시지를 보내지 않고 그룹 토픽에 한 번만 보냅니다. 시·군·구 명령은 그 아래 법정동 수만큼만 나갑니다.
- 오프라인 단말에는 보내지 않고 기다리지도 않습니다. 결과 화면에는 오프라인이라 보내지 않았다고 따로 표시합니다.
- 그룹 스케줄 보내기는 초당 10대, 펌웨어 갱신은 동시 10대와 낮 시간대로 속도를 제한합니다. 1만 대에 동시에 일을 시키지 않는 것이 원칙입니다.
- 단말이 상태를 보내는 순간을 기회로 삼아 대기 중인 작업을 바로 이어 갑니다. 그래서 1만 대를 주기적으로 훑는 무거운 타이머가 필요 없습니다.

### 5.5 온라인 판정

이 모뎀은 MQTT의 유언 메시지 기능을 지원하지 않아서, 단말이 끊겨도 서버가 알 방법이 없었습니다.
브로커의 접속·끊김 로그를 백엔드가 실시간으로 읽어 온라인 여부를 판단하고, 로그를 놓친 경우를 대비해 마지막 수신 시각이 보고 주기의 3배를 넘으면 오프라인으로 보는 규칙을 함께 두었습니다.
로그 파일이 커지면 브로커 쪽 감시 루프가 잘라 내고, 백엔드는 파일 크기가 줄어든 것을 보고 처음부터 다시 읽습니다.

### 5.6 검증

- 가상 단말 시뮬레이터를 직접 만들어 실제 모뎀 없이도 사양대로 동작하는 단말 수백 대를 띄웁니다.
- 재접속 폭주 시나리오는 단말을 승인한 뒤 한꺼번에 끊고 10초 안에 다시 붙여, 승인 없이 retain만으로 운전이 재개되는지, 서버 상태 확인이 한 번도 실패하지 않는지, 저장 실패가 늘지 않는지를 자동으로 확인합니다.
- 명령 폭주 시나리오에서는 200대에 시·군·구 명령을 보내 0.4초 안에 전원 응답을 받고, 서버 발행량이 상한을 넘지 않음을 확인했습니다.
- 개발 PC의 Docker 환경 한계로 폭주 시험은 300대까지 돌렸고, 1만 대 성능 시험은 운영 사양 서버에서 진행할 항목으로 남겨 두었습니다.

## 6. 보안 설계

- **단말 인증**: 단말 비밀번호는 어디에도 저장하지 않습니다. 서버 비밀키와 단말 UUID로 HMAC-SHA256을 계산한 값이 비밀번호이고, 단말은 부팅 때 계산하며 브로커는 접속 순간 같은 값을 계산해 비교합니다. 새 단말을 미리 등록하지 않아도 되고 비밀번호 파일이 유출될 일도 없습니다. 키를 여러 개 동시에 허용해 무중단 키 교체가 가능합니다.
- **토픽 권한**: 단말은 자기 UUID 토픽에만 쓰고, 자기 명령 토픽과 자기 그룹 토픽만 읽습니다.
- **전송 암호화**: 단말은 MQTT over TLS 8883, 관리 화면은 HTTPS와 HSTS를 씁니다.
- **OTA 주소**: 단말 모뎀은 HTTPS 인증서를 검증하지 못합니다. 그래서 다운로드 주소를 단말과 명령마다 다른 무작위 22자로 만들고 2시간만 유효하게 했으며, 파일의 위조 여부는 검증된 MQTT 채널로 따로 보낸 SHA-256으로 단말이 확인합니다.
- **관리 화면**: 세션 쿠키 서명, 비밀번호 PBKDF2 해시, 5회 실패 잠금, 무동작 자동 로그아웃, 권한과 지역 범위 검사를 한 곳에서 처리합니다.

## 7. 개발 과정

### 7.1 단계별 진행

단말과 서버가 함께 합격해야 다음 단계로 넘어가는 방식으로 진행했습니다.

| 단계 | 내용 |
|---|---|
| 1차 | 브로커만 띄워 실제 단말의 MQTT 접속을 확인했습니다 |
| 2차·3차 | 상태 수집, 단말별 HMAC 인증, 승인 흐름, 설정 동기화, 온라인 판정을 만들었습니다 |
| 4차 | 운영 브로커를 분리하고 TLS 8883으로 옮겼습니다 |
| 5차 | 법정동 트리, 그룹 원격 제어, 권한을 만들었습니다 |
| 6차 | 단말 설정 원격 읽기·쓰기, 알람, 그룹 스케줄, 대시보드를 만들었습니다 |
| 7차 | 지도, 통계, 계정 3단계, 공공 보안 항목, 설치형 납품 묶음, OTA를 만들었습니다 |

### 7.2 결정을 기록하며 개발

설계를 바꾸는 결정은 모두 `docs/decisions/`에 ADR로 남겼습니다. 지금까지 13개의 기록이 있습니다.
예를 들면 다음과 같은 결정입니다.

- 1만 대 규모에서 EMQX나 클러스터 대신 Mosquitto 단일 인스턴스와 단일 백엔드 프로세스를 택한 이유
- 설정값을 retain으로 보관하지 않고, 단말이 되돌려 보내는 설정 번호를 비교해 다시 보내는 방식으로 바꾼 이유
- 비밀번호 파일 방식에서 HMAC 계산 비밀번호와 인증 플러그인으로 바꾼 이유
- 유언 메시지 대신 브로커 로그로 온라인을 판정하게 된 이유

### 7.4 사용자의 말로 만든 화면

처음에는 개발 용어가 화면에 그대로 드러났습니다. 스케줄 배포, 프로필, 노드 같은 말입니다.
현장 운영자가 읽는다는 관점으로 그룹 스케줄 변경, 스케줄 양식, 지역 같은 말로 모두 바꿨고, 영어 오류 코드 대신 무엇을 고치면 되는지 알려 주는 한국어 문구를 쓰는 것을 원칙으로 삼았습니다.
조작 방식도 새로 배우지 않도록 파일 탐색기처럼 왼쪽 트리에서 고르고 오른쪽에서 작업하는 익숙한 형태로 통일했습니다.

### 7.5 클라우드에 묶이지 않는 납품

공공기관 납품을 염두에 두고 AWS 전용 기능에 대한 의존을 점검해 걷어 냈습니다.
프로그램 전체를 Docker 이미지로 묶은 설치 파일 하나를 만들어, 인터넷이 없는 기관 서버에서도 스크립트 하나로 설치와 업데이트를 할 수 있습니다.
기관이 국내 인증 클라우드를 직접 계약하고 그 위에 소프트웨어를 설치해 넘기는 방식을 기준으로 설계했습니다.

## 8. 협업 방식: MCP 서버로 연결한 문제점 시트

단말 개발자와 서버 개발자는 서로 다른 저장소에서 일합니다.
두 사람이 공유하는 것은 단말 쪽이 관리하는 통신 사양서와, 문제점과 요청을 주고받는 구글 시트 하나입니다.

### 8.1 시트 구조

시트의 한 행이 하나의 문제점이나 요청입니다.

- 단말 개발자는 문제와 대책을 적고, 보조설명 칸에 추가 의견을 씁니다.
- 서버 개발자는 비고 칸에 날짜를 붙여 회신을 덧붙입니다.
- 상태 칸은 등록, 확인중, 미수정, 완료 같은 진행 단계를 나타내며, 완료 판정은 요청한 쪽이 합니다.
- 사양처럼 긴 내용은 연결 탭에 따로 적습니다.

### 8.2 MCP 서버

이 시트를 AI 코딩 에이전트가 직접 읽고 쓸 수 있도록 작은 MCP 서버를 만들어 Claude Code에 연결했습니다.

| 도구 | 하는 일 |
|---|---|
| `list_issues` | 끝나지 않은 문제점 목록을 가져옵니다 |
| `get_issue` | 한 건의 전체 내용과 연결 탭의 사양 본문을 가져옵니다 |
| `append_comment` | 내 칸에만 날짜를 붙여 회신을 덧붙입니다 |
| `add_issue`, `set_status` | 새 항목을 등록하고 상태를 바꿉니다 |

MCP 서버 자체에 역할 규칙을 넣었습니다. 서버 PC는 비고 칸에만 쓰고 상대의 보조설명 칸은 건드리지 않으며, 링크로 공유되는 문서이므로 비밀번호와 IP와 키는 절대 적지 않습니다.

### 8.3 하루의 흐름

1. 서버 개발자가 시트를 읽고 작업하라고 지시하면, 에이전트가 끝나지 않은 항목을 가져와 새 요청과 새 의견을 추립니다.
2. 사양이 바뀐 항목은 사양 본문과 기존 코드를 비교해 영향 범위를 찾고, 모호한 부분은 단말 쪽에 물을 질문 목록으로 정리합니다.
3. 코드를 고치고, 단위 시험을 돌리고, 로컬 Docker 환경과 브라우저에서 고친 기능을 직접 확인합니다. OTA처럼 단말이 있어야 하는 기능은 가짜 단말 스크립트를 만들어 처음부터 끝까지 흘려 봅니다.
4. 관련 문서와 보고서를 고칩니다.
5. 시트 비고 칸에 무엇을 바꿨고 무엇을 확인했는지, 단말 쪽이 결정할 것이 무엇인지 회신합니다. 단말 쪽이 서버 의견을 물은 항목에는 근거를 들어 의견을 적습니다.
6. 커밋과 운영 서버 배포는 서버 개발자가 직접 합니다. 에이전트는 운영 서버에 접근하지 않습니다.

### 8.4 이렇게 일해서 얻은 것

- 한 달 남짓한 기간에 50건이 넘는 문제점과 요청을 처리했고, 모든 회신이 시트 한 곳에 날짜순으로 남아 있습니다.
- 프로토콜은 단말 쪽 사양서가 기준이고 서버는 임의로 바꾸지 않는다는 원칙을 지켰습니다. 바꿔야 할 때는 시트로 제안하고, 단말 쪽이 사양서에 확정한 뒤 반영했습니다.
- OTA처럼 큰 기능은 서버가 보안과 동시 진행 대수에 대한 의견을 먼저 내고, 단말 쪽이 실기 실험 결과로 답하고, 합의된 결론으로 서버가 구현하는 순서로 진행했습니다. 다운로드 조각 크기와 주소 길이처럼 모뎀 실험으로만 알 수 있는 값은 단말 쪽 결과를 기다려 반영했습니다.
