## 1. 실행 방법

```bash
# 최초 1회 (Python 3.10+, backend 와 별도 venv)
python -m venv tools/.venv
tools/.venv/Scripts/python -m pip install -r tools/requirements.txt     # Linux: tools/.venv/bin/python

# 서비스 기동 (infra 담당, docs/04)
docker compose --profile local-db up -d

# 시나리오
tools/.venv/Scripts/python -m tools.scenarios.run --list
tools/.venv/Scripts/python -m tools.scenarios.run --all --phase-only 2 --report tools/scenarios/out/s2.md
tools/.venv/Scripts/python -m tools.scenarios.run --all --phase-only 3 --allow-docker --report tools/scenarios/out/s3.md
tools/.venv/Scripts/python -m tools.scenarios.run --only S2-04,S3-02
tools/.venv/Scripts/python -m tools.scenarios.run --all --allow-docker            # 2·3차 전부(S2-11/S2-12/S3-04 포함)
tools/.venv/Scripts/python -m tools.scenarios.run --all --phase 5                 # 5차 그룹 CMD 까지

# 시뮬레이터 단위 시험 (서비스 없이)
tools/.venv/Scripts/python -m pytest tools/tests

# 단말 시뮬레이터만 (부하·수동 확인) — 2cha = 1.4.0, 승인은 서버 화면/REST 로
tools/.venv/Scripts/python -m tools.sim.fleet --count 100 --ti 60
tools/.venv/Scripts/python -m tools.sim.fleet --count 1000 --storm --storm-window 10 --cut-after 60
tools/.venv/Scripts/python -m tools.sim.fleet --count 3 --ka 10 --time-scale 60   # 끊김 감지·재전송 빨리 보기
tools/.venv/Scripts/python -m tools.sim.fleet gen-passwords --count 3             # uuid,HMAC 비밀번호 (mosquitto_pub 확인용)
tools/.venv/Scripts/python -m tools.sim.monitor                                   # iotlight/# 감시 + 사양 위반 표시
```

러너 옵션:

| 옵션 | 뜻 |
|---|---|
| `--list` | 목록만. 서비스 없이 동작 |
| `--all` / `--only A,B` / `--phase-only N` | 실행 대상. 2·3차는 항상 열려 있다(단말 1.4.0 은 승인 게이트가 항상 ON) |
| `--phase 5` | 5차 기능 플래그(`group_cmd`)를 연다. 없으면 S5-01 SKIP |
| `--allow-docker` | `docker compose restart/stop/start` 를 부르는 시나리오(S2-11, S2-12, S3-04) 허용 |
| `--sim-mode auto\|1cha\|2cha` | `auto` = `2cha`(HMAC 계정, 서버 준비 불필요). `1cha` 는 공용 계정·1차 펌웨어 모양(공용 계정이 살아 있을 때만) |
| `--report 경로` | 마크다운 보고서(판정표 + 실패 로그) |
| `--keep-rows` | 시험 뒤 DB 행을 남긴다(디버깅) |
| `--storm-count N` | S2-10 단말 수(기본 1000) |

종료 코드: PASS 만 있으면 0, FAIL/ERROR 가 있거나 실행된 것이 없으면 1. 서비스가 내려가 있으면 전부 SKIP(이유 표시) — 러너는 죽지 않는다.

### 승인은 setup 에서 이렇게 한다

단말 1.4.0 은 `REGISTER_ACK state=ACTIVE` 를 받기 전에는 Telemetry 를 보내지 않는다(§3.4). 계정 파일·CSV 같은 서버 쪽
사전 준비는 없다(HMAC 은 양쪽이 계산). Telemetry 가 필요한 시나리오는 `make_devices(ctx, n, approve_now=True)` 로 만든다:

1. 단말 접속 → REGISTER → 서버가 행을 만들고 `REGISTER_ACK PENDING` retain (`wait_rows` 로 행 생성을 기다린다 — 행이 없으면 PATCH 는 404)
2. `PATCH /api/devices/{uuid}/state {"state":"ACTIVE","site":…}` (병렬 20, `common.approve`)
3. 단말이 retain/실시간 ACTIVE 를 받을 때까지(`SimDevice.wait_state("ACTIVE")`) → TM 1건 즉시 → 서버 `cv_server` 0→1 → 첫 TM 직후 `CONFIG_SET cv=1`

그래서 승인된 단말은 시나리오 본문 전에 이미 **CONFIG_SET 1회·CONFIG_ACK OK 1회**를 겪었다. CONFIG 횟수를 세는 시나리오는
그 시점의 `stats.config_set_rx` 를 기준값으로 잡는다. 시뮬레이터로 승인 retain 을 직접 발행하는 일은 하지 않는다(서버 계정으로
쓰면 되지만 그러면 서버의 승인 로직을 시험하는 것이 아니다). fleet 을 별도 프로세스로 띄우는 S2-10 은 `approve_uuids` 로 같은 일을 한다.

### 시뮬레이터 UUID 대역

`51A0` + 네임스페이스 4자리 + 순번 16자리. 네임스페이스는 시나리오 번호(`S2-03` → `0203`)라 브로커 로그·DB 에서 어느 시나리오의 단말인지 바로 보이고, 시나리오끼리 레코드를 건드리지 않는다. 시험이 끝나면 `DELETE /api/devices/{uuid}`(빈 retain 까지) + DB 행 삭제로 정리한다(`--keep-rows` 로 남길 수 있다).

### Windows 주의

aiomqtt 는 selector 이벤트 루프가 필요하고 Windows 의 `select()` 는 소켓 512개가 한계다. `fleet` 은 400대를 넘으면 자동으로 프로세스를 나눈다(`--workers`). S2-10(1,000대)은 이 방식으로 돈다. 리눅스는 한 프로세스로 되지만 `ulimit -n` 을 올려야 한다.

> **Windows + Docker Desktop 에서는 S2-10 을 `--storm-count 300` 이하로 돌린다.** 1,000대를 호스트에서
> 컨테이너 포트로 몰아넣으면 Docker Desktop 의 호스트 포트 프록시가 멈춰 8000/1883 이 전부
> 타임아웃되고, 복구하려면 Docker Desktop 을 재시작해야 한다(2026-09-25 실측 — 브로커·백엔드는
> 멀쩡했다). 1,000대·1만 대 폭주는 리눅스(EC2)에서 돌린다. 그때 발견한 것: aircast 값
> `max_queued_messages 200` 으로는 백엔드 구독 연결에서 메시지가 버려진다 → 10000 으로 올렸다.
> go-auth 로 바꾼 뒤에는 1,000대 재접속 폭주가 `/internal/mqtt/auth` 1,000회 = 백엔드 HTTP 부하이기도 하다(캐시 600초).

## 3. 시나리오 목록

판정 규칙: DB(정본)를 asyncpg 로 직접 읽고 REST 로 교차 확인. 고정 대기는 2초 이하, 나머지는 조건 폴링(`wait_until`, 상한 있음).
"승인됨" = setup 에서 위 절차로 ACTIVE 로 만든 단말. 3차 시나리오는 `time_scale=60`(5분 → 5초, 30분 → 30초, 재접속 30초 → 0.5초).

### 2차 — 수집 서비스 + DB + 계정 + CONFIG (`--phase-only 2`)

| ID | 목적 | 절차 | 합격 기준 |
|---|---|---|---|
| S2-01 | 신규 단말 REGISTER→승인→TELEMETRY→DB | 50대 2cha, ti=5s. PENDING 확인 → 승인 → 15초 이상 | 승인 전 행이 REGISTER 필드(fw/model/imei/iccid/msisdn/cv/ti/**ka_device**)로 채워지고 state=PENDING·cv_server=0·TM 0건 → 승인 뒤 state=ACTIVE·site, telemetry 건수 = 1+경과/ti ±2, `last_telemetry_at` 3회 단조 증가, 적재율 ≥95%, cv_device==cv_server≥1, REST 상세의 `last_telemetry.sq/bv/ts`·계산 필드(`ti_effective`…) 그리고 **목록(`?q=`)에도 `last_telemetry`**·`counts` |
| S2-02 | REGISTER 유실 | 정상 REGISTER→승인(retain ACTIVE) 뒤 **DB 행만 삭제** → REGISTER 없이 재부팅 → retain ACTIVE 로 TM | TM 만으로 행 생성(last_register_at/device_model/ka_device NULL, last_telemetry_at 설정) → 늦은 REGISTER 로 imei/ti_device/ka_device/last_register_at·register_ack_at 채워짐 |
| S2-03 | sq 판정 | 승인됨. drop 3 → 같은 sq 중복 → 재부팅(retain 으로 복귀) → 별도 단말 wrap(2³²-2 → 2³²-1 → 0 → 1 → 재부팅) → 큰 점프(1 → 2³²-2) | lost_count +3(reboot 불변), 중복은 카운트 없음 → reboot_count +1·REBOOT 이벤트 1건·last_sq=0 → wrap 은 reboot 0·lost 0(또는 점프 상한), wrap 뒤 진짜 재부팅은 reboot_count 1 → 큰 점프는 lost 증가 ≤ gap·int32 안·flush 실패 없음 |
| S2-04 | CONFIG 왕복(전체값) | 승인됨 2대(하나는 cv=7 로 시작). PATCH `{ti_override:300}` → PATCH 10/3601·ka 1801 → 원시 CONFIG_SET ti=10 | 승인 직후 CONFIG_SET **cv=1**·cv/ti/ka 전부·lat/lon 키 없음 → PATCH 응답 `published=true`·`ti_effective=300`, CONFIG_SET(ti 300, ka 프로필값, cv 증가)·ACK OK·단말 ti=300·cv==cv_server·config_sent_at → 다음 TM cv 일치 → DB 수렴, 이번 cv 의 CONFIG_ACK 이벤트 1건, `config_pending=false`·`config_mismatch=false` / 422 `VALIDATION_FAILED`·cv_server 불변·CONFIG_SET 미발행 / 단말 RANGE·cv·ti 유지·RANGE 이벤트 / cv=7 단말은 승인 뒤 CONFIG_SET cv=**8**, DB cv_server=8 |
| S2-05 | CONFIG 재전송 + FLASH | 승인됨. `ignore_config_set=1` → PATCH → 2초마다 TM 90초 → 수렴 → `flash_fail_next=1` → PATCH | 즉시 1회(무시) → 쿨다운(≥50s) 뒤 TM 시점에 정확히 1회 재전송 → 적용·DB 수렴 → TM 3회에 재전송 없음 → FLASH 응답 뒤 이전 값 유지, **다음 TM 에 바로 재전송(30s 안, 쿨다운 없음)** → OK·적용, FLASH 이벤트 기록 |

## 4. 시나리오 추가하는 법

1. `tools/scenarios/phaseN.py` 에 async 함수를 쓰고 `@scenario("SN-xx", "제목", phase=N, timeout=…, requires=…, docker=…)` 로 등록한다. docstring 에 목적과 합격 기준을 적는다(러너 `--list` 와 이 문서의 근거).
2. 단말은 `make_devices(ctx, n, ti=…, approve_now=True, **플래그)` 로 만든다 — 시나리오 네임스페이스 UUID, HMAC 계정, (옵션) REST 승인, 종료 시 stop + 행 삭제가 자동 등록된다. 추가 정리는 `ctx.defer(fn)`.
3. 판정은 `ctx.check(cond, "설명")`, `ctx.check_eq(a, b, "설명")`, 조건 대기는 `ctx.wait_until(pred, timeout=…, what="…")`. 고정 대기는 `ctx.hold(≤2s, 이유)` 만. CONFIG_SET 모양은 `check_config_set_shape`, §1.1.10 지연은 `rx_delay`.
4. 전제가 안 맞으면 `ctx.skip("이유")`. 미확정 REST(5차)는 404/405 를 SKIP 으로 돌린다(phase5 `_post_cmd` 참고).
5. `tools/tests/test_fleet_and_framework.py::test_registry_has_all_required_scenarios` 에 ID 를 추가하고 이 문서 표에 한 줄 넣는다.
6. `python -m tools.scenarios.run --only SN-xx` 로 실제 서비스에 대고 돌려본 뒤 커밋한다.
