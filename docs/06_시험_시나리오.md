# 06. 시험 시나리오

- 코드: `tools/sim/`(단말 시뮬레이터), `tools/scenarios/`(시나리오 러너), `tools/tests/`(시뮬레이터 단위 시험)
- 원칙(CLAUDE.md): 큰 단계가 끝날 때마다 시나리오를 **실제로 돌려** 확인한다. 로컬에서 돌려보지 않은 기능은 완료가 아니다.
- 시뮬레이터는 사양서 §1.1, §3, §3.10.7, §16.1 을 그대로 흉내낸다. 백엔드·인프라 코드를 import 하지 않고 브로커·DB·REST 로만 말한다.

## 1. 실행 방법

```bash
# 최초 1회 (Python 3.10+, backend 와 별도 venv)
python -m venv tools/.venv
tools/.venv/Scripts/python -m pip install -r tools/requirements.txt     # Linux: tools/.venv/bin/python

# 서비스 기동 (infra 담당, docs/04)
docker compose --profile local-db up -d

# 시나리오
tools/.venv/Scripts/python -m tools.scenarios.run --list
tools/.venv/Scripts/python -m tools.scenarios.run --all --report tools/scenarios/out/report.md
tools/.venv/Scripts/python -m tools.scenarios.run --only S2-01,S2-03
tools/.venv/Scripts/python -m tools.scenarios.run --all --allow-docker            # S2-11/S2-12 포함
tools/.venv/Scripts/python -m tools.scenarios.run --all --phase 3 --allow-docker  # 3차 시나리오까지
tools/.venv/Scripts/python -m tools.scenarios.run --all --phase 5                 # 5차 그룹 CMD

# 시뮬레이터 단위 시험 (서비스 없이)
tools/.venv/Scripts/python -m pytest tools/tests

# 단말 시뮬레이터만 (부하·수동 확인)
tools/.venv/Scripts/python -m tools.sim.fleet gen-accounts --count 100 --out accounts.csv
tools/.venv/Scripts/python -m tools.sim.fleet --count 100 --ti 60 --mode 2cha --accounts accounts.csv
tools/.venv/Scripts/python -m tools.sim.fleet --count 1000 --mode 1cha --storm --storm-window 10 --cut-after 60
tools/.venv/Scripts/python -m tools.sim.monitor          # iotlight/# 감시 + 사양 위반 표시
```

러너 옵션:

| 옵션 | 뜻 |
|---|---|
| `--list` | 목록만. 서비스 없이 동작 |
| `--all` / `--only A,B` / `--phase-only N` | 실행 대상 |
| `--phase 3`, `--phase 5` | 그 단계 기능 플래그(`approval_gate`, `group_cmd`)를 연다. 없으면 해당 시나리오 SKIP |
| `--allow-docker` | `docker compose restart/stop/start` 를 부르는 시나리오 허용 |
| `--sim-mode auto\|1cha\|2cha` | 시뮬레이터 계정. `auto` = `MQTT_TEST_ACCOUNT_ENABLED` 가 true 면 공용 계정(1cha), 아니면 CSV import 후 단말별 계정(2cha) |
| `--report 경로` | 마크다운 보고서(판정표 + 실패 로그) |
| `--keep-rows` | 시험 뒤 DB 행을 남긴다(디버깅) |
| `--storm-count N` | S2-10 단말 수(기본 1000) |

종료 코드: PASS 만 있으면 0, FAIL/ERROR 가 있거나 실행된 것이 없으면 1. 서비스가 내려가 있으면 전부 SKIP(이유 표시) — 러너는 죽지 않는다.

### 시뮬레이터 UUID 대역

`51A0` + 네임스페이스 4자리 + 순번 16자리. 네임스페이스는 시나리오 번호(`S2-03` → `0203`)라 브로커 로그·DB 에서 어느 시나리오의 단말인지 바로 보이고, 시나리오끼리 레코드를 건드리지 않는다. 시험이 끝나면 `DELETE /api/devices/{uuid}` + DB 행 삭제로 정리한다(`--keep-rows` 로 남길 수 있다).

### Windows 주의

aiomqtt 는 selector 이벤트 루프가 필요하고 Windows 의 `select()` 는 소켓 512개가 한계다. `fleet` 은 400대를 넘으면 자동으로 프로세스를 나눈다(`--workers`). S2-10(1,000대)은 이 방식으로 돈다. 리눅스는 한 프로세스로 되지만 `ulimit -n` 을 올려야 한다.

## 3. 시나리오 목록

판정 규칙: DB(정본)를 asyncpg 로 직접 읽고 REST 로 교차 확인. 고정 대기는 2초 이하, 나머지는 조건 폴링(`wait_until`, 상한 있음).

### 2차 — 수집 서비스 + DB + 계정 + CONFIG

| ID | 목적 | 절차 | 합격 기준 |
|---|---|---|---|
| S2-01 | 신규 단말 REGISTER→TM→DB | 50대, ti=5s, 15초 이상 | device 행이 REGISTER 필드(fw/model/imei/iccid/cv/ti)로 채워짐, state=ACTIVE, telemetry 건수 = 1+경과/ti ±(2,1), `last_telemetry_at` 3회 단조 증가, 전체 적재율 ≥95%, REST `last_telemetry.sq/bv/ts` == 마지막 발행 |
| S2-02 | REGISTER 유실 | REGISTER 없이 TM 만 → 나중에 REGISTER | TM 만으로 행 생성(last_register_at NULL, device_model NULL, last_telemetry_at 설정) → 늦은 REGISTER 로 imei/ti_device/last_register_at 채워짐 |
| S2-03 | sq 판정 | drop 3 → 같은 sq 중복 → 재부팅 → 별도 단말로 wrap(첫 TM 2³²-2 → 2³²-1 → 0 → 1 → 재부팅) → 큰 점프(1 → 2³²-2) | lost_count +3(reboot 불변), 중복은 카운트 없음 → reboot_count +1·REBOOT 이벤트 1건·last_sq=0 → wrap 은 reboot 0·lost 0, wrap 뒤 진짜 재부팅은 reboot_count 1 → 큰 점프는 lost 증가 ≤ gap·int32 안·flush 실패 없음 |
| S2-04 | CONFIG 왕복 | PATCH ti=300 → PATCH ti=10/3601 → 원시 CONFIG_SET ti=10 | CONFIG_SET 수신·ACK OK·단말 ti=300·cv==cv_server·config_sent_at, 다음 TM cv 일치 → DB 수렴, CONFIG_ACK 이벤트 1건 / 서버 4xx·cv_server 불변·CONFIG_SET 미발행 / 단말 RANGE·cv·ti 유지·서버가 RANGE 이벤트 기록 |
| S2-05 | CONFIG 재전송 | 단말이 첫 CONFIG_SET 무시, 2초마다 TM 90초 | 즉시 1회 → 쿨다운(≥50s) 뒤 TM 시점에 정확히 1회 재전송 → 단말 적용·DB 수렴 → 이후 TM 3회에 재전송 없음 |
| S2-06 | 단말별 계정 + ACL | CSV 20건 import → 접속 → 남의 topic 발행 | `imported=20`, ACL 적용 뒤 20대 접속, 틀린 비밀번호 거부, (공용 계정 꺼져 있으면) 공용 계정 거부, ACL 위반 발행 후 연결 유지·상대 telemetry 건수/last_sq 불변·유령 UUID 행 없음 |
| S2-07 | payload 이상 | 깨진 JSON, uuid 불일치 REGISTER, 64KB TM, 배열, 필드 누락 TM, 모르는 type, `"t":"TM"` | /health ok 유지, 단말 연결 유지, metrics 거부 카운터 증가, FFFF… 행 없음, `t` 키 TM 이 telemetry 로 적재, 정상 TM 계속 적재 |
| S2-08 | QoS1 중복 | PONG 3회 중복, CONFIG_ACK 3회 중복 | 각각 device_event 정확히 1행, dedup_key 채워짐, command.acked_count=1 |
| S2-09 | PING/PONG | ping 2회 + 무응답 단말 ping | seq 전역 단조 증가, command(seq) acked_count=1·result=OK·target/type/finished_at, PONG 이벤트 2건, 무응답은 60초 안에 TIMEOUT(참고 항목) |

| S2-11 | 브로커 재시작 `docker` | 20대 ti=5 → `restart mosquitto` | 단말이 끊김 감지 → backoff 재접속(접속 횟수 ≥2) → 재시작 이후 20대 모두 새 TM 적재(백엔드 재구독), REGISTER 재반영, /health ok |
| S2-12 | DB 장애 중 수신 `docker` | 100대 ti=5, `stop postgres` 30초 → `start` | 정지 중 /health 응답 ≥12/15, telemetry_dropped 증가, 단말 연결 유지 → 복구 뒤 90% 이상 단말 새 TM, /health ok |
| S2-13 | LWT vs 지연 TM | A 강제 절단 / B TM 직후 같은 초에 절단 / LWT 미지원 단말 절단 | LWT 이벤트(uuid 일치)·online=false·offline_at 기록 / B: TM 적재되지만 online false 유지, last_telemetry_at ≤ offline_at, last_seen_at ≥ last_telemetry_at / LWT 이벤트 없음 |
| S2-14 | 시각·단위 | TM 1건 | ts_device 원문(`YYMMDDThhmm`), bv/bi/sc/pp/li/cs/er/md/on/fw/ss/cv/pw1~3 원값(÷100 없음), raw == 원본, received_at 이 DB 시각 범위·timestamptz |

**S2-03 wrap 기대 동작**: `backend/app/mqtt/sq.py` 규칙을 따른다 — 직전 값이 uint32 상한 1,000 안쪽이고 새 값이 0 근처면 wrap(유실 = 연속분, 재부팅 아님), 그 밖의 감소는 재부팅. 단, 작은 sq 에서 2³²-2 로 점프하면 `lost = 4.29e9` 가 되어 `device.lost_count int` 를 넘긴다 — 서버가 gap 을 상한으로 자르거나 컬럼을 bigint 로 두어야 하며, 어느 쪽이든 flush 실패로 TM 이 버려지면 안 된다(시나리오 마지막 단계가 이것을 본다).

## 4. 시나리오 추가하는 법

1. `tools/scenarios/phaseN.py` 에 async 함수를 쓰고 `@scenario("SN-xx", "제목", phase=N, timeout=…, requires=…, docker=…)` 로 등록한다. docstring 에 목적과 합격 기준을 적는다(러너 `--list` 와 이 문서의 근거).
2. 단말은 `make_devices(ctx, n, ti=…, **플래그)` 로 만든다 — 시나리오 네임스페이스 UUID, 종료 시 stop + 행 삭제가 자동 등록된다. 추가 정리는 `ctx.defer(fn)`.
3. 판정은 `ctx.check(cond, "설명")`, `ctx.check_eq(a, b, "설명")`, 조건 대기는 `ctx.wait_until(pred, timeout=…, what="…")`. 고정 대기는 `ctx.hold(≤2s, 이유)` 만.
4. 전제가 안 맞으면 `ctx.skip("이유")`. 미확정 REST 는 404/405 를 SKIP 으로 돌린다(phase3 `_set_state` 참고).
5. `tools/tests/test_fleet_and_framework.py::test_registry_has_all_required_scenarios` 에 ID 를 추가하고 이 문서 표에 한 줄 넣는다.
6. `python -m tools.scenarios.run --only SN-xx` 로 실제 서비스에 대고 돌려본 뒤 커밋한다.
