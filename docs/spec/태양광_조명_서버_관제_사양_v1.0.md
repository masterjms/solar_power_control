원칙:

- **평문은 4차 전까지, 시험 Broker + 접속원 IP 제한 상태에서만.** 시험 단말
  외의 단말은 4차 전에 현장에 두지 않는다.
- **단말별 계정은 TLS와 별개로 2차에서 넣는다.** 공용 계정은 1차 전용이다.
- **서버 로직은 전송 방식에 의존하지 않게 만든다.** 4차 TLS 전환 시 서버
  코드는 접속 설정만 바뀌어야 한다.
- 각 단계는 앞 단계 합격 후 시작한다. 단, §0.4의 병렬 조사 항목은 단계와
  무관하게 먼저 착수한다.

### 0.1 왜 이렇게 나누는가

**1차의 목적은 통신 경로가 뚫리는지 확인하는 것뿐이다.**
LTE 망 등록 → DNS → TCP → MQTT 인증 → 메시지 왕복까지가 되는지 본다.
여기서 막히면 그 위에 무엇을 얹어도 소용이 없다.

**승인은 전송 방식과 무관하다.** 승인 로직(3차)은 평문에서 먼저 만들고
TLS(4차)는 그 위에 얹는다. 단말 신원을 보증하는 것은 TLS가 아니라 **2차의
단말별 계정**이다(§1.1.2.2). TLS는 그 계정이 평문으로 지나가는 것을 막는
층이다. 순서는 계정 → 승인 → TLS 다.

TLS를 먼저 하면 서버 일정이 모뎀 TLS 조사(§0.4 P-1)에 걸린다. 2·3차 서버
로직은 전송에 무관하므로 조사 결과를 기다릴 이유가 없다.

### 0.2 모뎀 구독 한도가 설계를 제한한다

**WD-N522S는 MQTT 구독 topic을 6개까지만 등록할 수 있다.**
(AT Commands Guide v2.2 §7.1.6)

| # | topic | 단계 |
|---|---|---|
| 1 | `iotlight/device/<uuid>/cmd` | 1차 |
| 2 | `iotlight/device/<uuid>/config` | 2차 |
| 3 | `iotlight/group/<grp[0]>/cmd` | 5차 |
| 4 | `iotlight/group/<grp[1]>/cmd` | 5차 |
| 5 | `iotlight/all/cmd` | 5차 |
| 6 | 예비 | — |

`grp`는 **최대 2개**다. 3개면 예비가 없다. 스케줄 배포(6차)와 OTA(7차)는
새 topic을 쓰지 않고 `cmd` payload의 `type`으로 구분한다. 자세한 것은
§3.10.10에 있다.

### 0.3 1차 ~ 3차 시험 시 주의

**3차까지는 평문이다.** 시험 전용 Broker와 접속원 IP 제한 상태에서만
진행한다. 시험 단말 외의 단말을 4차 전에 현장에 두지 않는다.

1차에는 승인 게이트가 없어 단말이 REGISTER 직후 바로 Telemetry를 보낸다.
운영 Broker에 1차 펌웨어를 붙이면 미승인 단말의 데이터가 그대로 쌓인다.

LTE 무선 구간은 통신사가 암호화한다. 평문 노출 구간은 통신사 코어 → AWS
사이 인터넷 구간이다. 시험 단말 몇 대, 접속원 IP 제한 상태에서는 감수할 수
있고, 운영 규모에서는 불가하다.

### 0.4 병렬 조사 항목 (단계와 무관, 즉시 착수)

서버 개발과 별도로 진행한다. 결과가 4차·6차 설계를 결정한다.

| # | 항목 | 확인할 것 | 영향 |
|---|---|---|---|
| P-1 | WD-N522S TLS | MQTTS 지원 AT 명령, 루트 CA 저장 방식·개수·크기 한도, TLS 버전, SNI, 서버 검증 on/off | 4차 분기 (§1.2.3) |
| P-2 | WD-N522S LWT | `AT*WMQTCON` 계열에 Will 설정 파라미터 존재 여부 | 3차 Online/Offline 방식 (§16.1) |
| P-3 | 수신 버퍼 | `*WMQTRCV` 최대 payload 길이 | 6차 chunk 크기 (§13) |

| P-5 | 인증서 갱신 | LE 90일 갱신 시 모뎀 측 루트 CA는 그대로인지 (leaf 갱신만) | 4차 운영 (§1.2) |

## 1. 서버 기본 역할

서버는 단말의 실제 조명 운전을 직접 수행하지 않는다.

단말은 Standalone으로 독립 운전하며 서버는 다음 기능을 담당한다.

동일 펌웨어에서 DIP8(PD13)이 ON인 상태로 부팅된 경우에만 LTE/서버 기능을 사용한다.
DIP8이 OFF이면 Standalone/GPS 모드로 동작하며 서버 접속을 시도하지 않는다.

- 단말 등록 및 관리
- 지도 기반 위치 관리
- LTE / SIM 정보 관리
- 상태 관제
- Solar / Battery 모니터링
- 원격 LED 제어
- Schedule 생성 및 배포
- Alarm / Event 관리
- OTA
- 이력 관리

## 1.1 MQTT 통신 경로 검증 **[1차 · 2차]**

1차 개발에서는 전체 관제 기능보다 LTE 모뎀이 서버 MQTT Broker에 접속하는 것을 먼저 검증한다.
**1차에는 서버 응용 프로그램을 만들지 않는다.** Mosquitto와 `Tools/mqtt_test.py`만 쓴다.

이 장의 topic·payload·계정 규격은 **2차에서 고정한다.** 2차가 끝나면 3차 이후에도
바뀌지 않는다. 절마다 단계를 표시한다.

승인 절차는 §3에 따로 확정해 두었고 **3차에서 구현한다.**

> **1차에는 승인 게이트가 없다.**
> 단말이 REGISTER 직후 바로 Telemetry를 보내므로, 시험 전용 Broker와 시험
> 계정에서만 진행한다. 운영 Broker에 붙이면 미승인 단말 데이터가 쌓인다.

### 1.1.1 목표와 단계

#### 1차-A: 모뎀의 MQTT Broker 접속 확인 - 현재 최우선 목표

현재 단계의 핵심은 WD-N522S LTE 모뎀이 `infontech.co.kr:1883`에 접속하여 MQTT 연결 성공
응답을 받는 것이다. 서버는 웹, DB, 관제, MQTT 응용 프로그램을 아직 구현할 필요가 없으며
Mosquitto Broker만 정상 실행하면 된다.

1차-A 필수 범위:

- LTE Cat-M1 망 접속 및 IP 할당
- DNS `infontech.co.kr` 해석 및 TCP 1883 연결
- 공용 시험 ID/PW 인증
- MQTT Broker 접속 성공(`*WMQTCON:2`)
- Broker 로그에서 24자리 UUID Client ID 접속 확인

위 항목이 성공하면 **1차-A 완료**로 판정하고 즉시 1차-B 메시지 검증으로 진행한다.
REGISTER 또는 PING/PONG 실패 때문에 모뎀의 Broker 접속 성공 판정을 취소하지 않는다.

#### 1차-B: MQTT 메시지 왕복 확인 - 접속 성공 직후 진행

- 단말 시험 명령 topic 구독
- 단말 UUID, Firmware, LTE/SIM 기본정보 REGISTER 발행
- 서버 `PING` 발행 및 단말 `PONG` 응답
- QoS 1 송수신 확인

1차-B는 1차-A가 성공한 뒤 수행한다. 서버 응용 프로그램을 아직 개발하지 않았다면
SolarLTE 프로젝트의 `Tools/mqtt_test.py`를 간이 서버로 사용한다.

#### 1차-C: 주기 상태 보고 - 확인만 한다

승인 절차 없이 REGISTER 직후 바로 시작한다. 통신 경로와 JSON 파싱을 확인하는
것이 목적이며, 운영에서는 §3의 승인을 거친 뒤에만 보낸다(3차).

- 단말이 `device/<uuid>/status`를 설정 주기로 발행 (§1.1.6)
- 서버는 `mosquitto_sub -t 'iotlight/device/+/status'` 로 수신만 확인한다

**1차 합격 = 1차-A.** B, C는 같은 시험 세션에서 확인만 하고, 실패해도 1차-A
판정을 되돌리지 않는다. B, C의 실패는 2차 규격 작업의 입력이다.

#### 1차에서 하지 않는 것

| 항목 | 단계 | 규격 위치 |
|---|---|---|
| CONFIG_SET / CONFIG_ACK | **2차로 이관 확정** | §1.1.7 |
| 단말별 계정 (1차는 공용 `solarlte-test`) | 2차 | §1.1.2.2 |
| DB, 웹, 관제 화면 | 2차 이후 | §4, §19 ~ §21 |
| **PENDING / ACTIVE 승인 처리** | **3차** | **§3** |
| 승인 전 Telemetry 차단 | 3차 | §3.4 |
| 설치 위치 배정 / 그룹 배정 | 3차 / 5차 | §3.1, §3.10 |
| TLS 인증서 및 MQTTS | 4차 | §1.2 |
| 원격 LED 제어 | 5차 | §3.10, §17 |
| `SCHEDULE_UPDATE`로 372일 표 갱신 | 6차 | §9, §13 |
| `STATUS_GET` 즉시 조회 | 6차 | §16.4 |
| 저전압 임계값, 밝기 등 운전 설정의 서버 변경 | 6차 | §17 |
| Alarm | 6차 | §22 |
| OTA | 7차 | §18 |

1차에서 운전 설정은 **PC 설정 도구(`Tools/config_tool`)로만** 바꾼다.
Telemetry 주기(`ti`)도 마찬가지다. 서버가 바꾸는 것은 2차부터다.

### 1.1.2 Broker 및 Session 설정

| 항목 | 1차 설정 |
|---|---|
| Protocol | MQTT v3.1.1 |
| Host | `infontech.co.kr` |
| TCP Port | `1883` |
| Client ID | STM32 UUID 전체 24자리 대문자 16진수 |
| Keep Alive | 60초 |
| Clean Session | 1 |
| Username | `solarlte-test` (1차 공용. 2차부터 UUID, §1.1.2.2) |
| Password | `solarlte-test-2026` (1차 공용. 2차부터 단말별, §1.1.2.2) |
| Broker 익명 접속 | 사용하지 않음(`allow_anonymous false`) |
| QoS | 1 |
| Retain | 0 |

평문 MQTT 1883은 1차 ~ 3차 시험 Broker에만 사용한다. 운영 Broker는 4차 MQTTS 8883과
서버 인증서 검증을 적용한 뒤 사용한다(§1.2).

#### 1.1.2.1 ID / Password 적용 기준 **[1차]**

1차 MQTT 간이 검증은 모든 단말과 PC 시험 프로그램이 하나의 공용 시험 계정을 사용한다.

- MQTT Username: `solarlte-test`
- MQTT Password: `solarlte-test-2026`
- 단말 펌웨어 설정: 위 값을 `LTE_MQTT_USERNAME`, `LTE_MQTT_PASSWORD`에 설정
- Mosquitto 설정: 익명 접속 차단 및 공용 시험 계정 등록
- UUID: MQTT Client ID와 단말 식별값으로 사용하며, 로그인 ID가 아니다.
- 이 계정은 평문 MQTT 1883 간이 검증 전용이며 운영 서버에서 사용하지 않는다.

1차 Mosquitto 최소 설정 예시는 다음과 같다.

```conf
listener 1883
protocol mqtt
allow_anonymous false
password_file /etc/mosquitto/passwd
```

서버에서 다음 명령으로 공용 시험 계정을 생성한다. Password 입력 요청에는
`solarlte-test-2026`을 입력한다. `-c`는 기존 파일을 덮어쓰므로 최초 생성할 때만 사용한다.

```bash
sudo mosquitto_passwd -c /etc/mosquitto/passwd solarlte-test
```

Mosquitto를 재시작한 후 펌웨어와 PC 도구는 위 ID/PW로 접속한다. 서버가 모든 임의의
ID/PW를 무조건 허용하도록 만들 수도 있지만, 이는 실제 인증을 검사하지 않는 익명 접속과
같으므로 1차 기준으로 사용하지 않는다. 공용 계정 한 쌍을 사용하면 Username/Password
전달 경로와 Broker 인증 성공 여부까지 함께 검증할 수 있다.

1차 시험 Broker는 인터넷 전체에 공개하지 않고 AWS Security Group 또는 방화벽에서
시험에 필요한 접속원만 TCP 1883으로 접근하도록 제한한다.

공용 시험 계정을 변경하는 경우에는 시험 전에 다음 값을 모두 동일하게 변경해야 한다.

1. 서버 Mosquitto에 시험용 Username과 Password를 등록한다.
2. 펌웨어 `FW/Modules/lte_config.h`의 `LTE_MQTT_USERNAME`, `LTE_MQTT_PASSWORD`를 설정하고 다시 빌드한다.
3. PC 간이 서버에는 `MQTT_USERNAME`, `MQTT_PASSWORD` 환경변수로 같은 값을 전달한다.

```powershell
$env:MQTT_USERNAME = "test-user"
$env:MQTT_PASSWORD = "test-password"
python Tools\mqtt_test.py --device-uuid 00112233445566778899AABB --timeout 120
```

서버와 다른 인증값으로 접속하면 MQTT 연결 실패로 판정한다. 단말 로그에는
`MQTT CONNECTION FAILED` 또는 `MQTT FAIL REASON=4 (username/password)`가 표시될 수 있다.
운영용 Username과 Password 값은 본 사양서나 소스 저장소에 기록하지 않는다.

#### 1.1.2.2 단말별 계정과 ACL **[2차]**

**공용 계정은 2차 시작과 함께 폐기한다.** 단말 신원을 보증하는 것은 TLS가
아니라 이 계정이다(§0.1).

| 항목 | 확정 |
|---|---|
| Username | 단말 UUID 24자리 (Client ID와 동일) |
| Password | 단말별 무작위 문자열. PC 설정 도구(`cfg set mqtt_pw`)로 기록, `system_data`에 저장 |
| 서버 계정 | `server` 1개. `iotlight/#` readwrite |
| 배포 | PC 도구가 `uuid,password` CSV를 만들고 서버 DB에 import → `mosquitto_passwd` 갱신 |

Mosquitto ACL (`/etc/mosquitto/acl`):

```conf
user server
topic readwrite iotlight/#

pattern write iotlight/device/%u/register
pattern write iotlight/device/%u/status
pattern write iotlight/device/%u/result
pattern write iotlight/device/%u/event
pattern read  iotlight/device/%u/cmd
pattern read  iotlight/device/%u/config
pattern read  iotlight/group/#
pattern read  iotlight/all/cmd
```

- `%u`는 접속한 username으로 치환된다. 단말은 자기 UUID topic에만 쓸 수 있다.
- `group/#` 읽기는 전 단말에 열린다. 다른 그룹 명령을 구독해도 실행은 자기
  `grp` 목록으로 걸러지므로 위험은 낮다.
- 이것이 있어야 3차 승인 게이트가 **보안 기능**이 된다. 없으면 운영 편의
  기능일 뿐이다.

2차 합격 기준에 "다른 UUID topic에 발행 시도 → Broker가 거부"가 들어간다
(§1.1.8).

### 1.1.3 Topic

```text
iotlight / <scope> / <id> / <kind>
```

| 자리 | 값 | 뜻 |
|---|---|---|
| root | `iotlight` | 조명 IoT namespace. 전송 수단(LTE)이 아니라 기능으로 짓는다 |
| scope | `device` / `group` / `all` | 누구에게 가는가 |
| id | UUID 또는 `group_id`. `all` 은 생략 | 어느 대상인가 |
| kind | `register` `status` `result` `event` `cmd` `config` | 무엇인가 |

`{uuid}`는 STM32G0B0의 96-bit Unique ID 전체를 표현한 24자리 대문자 16진수이다.

사내 마을방송(`iotradio`)과 같은 규칙이다. 두 제품을 같은 관제 화면에서
다루게 되어도 topic 파서를 따로 만들지 않는다.

#### 단말 → 서버 (발행)

| 용도 | Topic | QoS | 단계 |
|---|---|---|---|
| 단말 기본정보 등록 | `iotlight/device/{uuid}/register` | 1 | 1차 |
| 주기 상태 보고 | `iotlight/device/{uuid}/status` | **0** | 1차 |
| 명령 응답 (PONG 1차, CONFIG_ACK 2차, CMD_ACK 5차) | `iotlight/device/{uuid}/result` | 1 | 1차 |
| LWT (§16.1) · 오류 flag 변화 통보 (§16.2) | `iotlight/device/{uuid}/event` | 1 | **3차 / 6차** |

#### 서버 → 단말 (구독)

| 용도 | Topic | QoS | 단계 |
|---|---|---|---|
| 개별 명령 (PING 1차, 점·소등 5차, 스케줄 6차, OTA 7차) | `iotlight/device/{uuid}/cmd` | 1 | 1차 |
| 설정 전달 (CONFIG_SET) | `iotlight/device/{uuid}/config` | 1 | **2차** |
| 승인 상태 통보 (REGISTER_ACK, retain) | `iotlight/device/{uuid}/config` | 1 | **3차** |
| 그룹 명령 | `iotlight/group/{group_id}/cmd` | 1 | **5차** |
| 전체 명령 | `iotlight/all/cmd` | 1 | **5차** |

**1차 펌웨어가 구독하는 것은 `device/{uuid}/cmd` 하나다.** `config` 구독은
2차에서 추가한다(구독 슬롯 2번째, §0.2).

스케줄 배포(6차)와 OTA(7차)는 **새 topic을 쓰지 않고 `cmd` payload의 `type`
으로 구분한다.** 모뎀 구독 한도가 6개이므로(§0.2) 위 다섯 개를 다 채워도
한 칸이 남는다.

응답은 종류를 나누지 않고 `result` 하나로 모은다. 발행은 구독 한도를 쓰지
않지만, 서버가 구독할 topic 수를 줄이면 관제 쪽 와일드카드가 단순해진다.
어느 명령에 대한 응답인지는 payload 의 `type` 과 `seq` 로 구분한다.

Telemetry만 QoS 0이다. 한 건을 놓쳐도 다음 주기에 만회되고, QoS 1로 올리면
모뎀이 PUBACK을 기다리는 동안 상태 머신이 묶여 PING 응답이 늦어진다.

서버 시험 프로그램은 `iotlight/device/+/register`로 신규 단말을 확인하거나,
시험할 UUID를 알고 있는 경우 `iotlight/device/{uuid}/#`만 구독할 수 있다.

### 1.1.4 REGISTER **[1차, 2차 확장]**

단말은 MQTT 연결 및 `device/{uuid}/cmd` 구독 성공 후 다음 메시지를 QoS 1로
한 번 발행한다.

```json
{
  "type": "REGISTER",
  "uuid": "00112233445566778899AABB",
  "fw": "1.0.0",
  "cv": 3,
  "ss": 15,
  "ti": 600,
  "device_model": "RMCB-1100M",
  "modem_model": "WD-N522S",
  "msisdn": "",
  "imei": "123456789012345",
  "iccid": "8982..."
}
```

- `uuid`, `fw`, `device_model`, `modem_model`, `msisdn`, `imei`, `iccid` key는 항상 포함한다.
- `cv`, `ss`, `ti`는 **2차에서 추가한다.** 현재 1차 펌웨어는 싣지 않는다.
  §1.1.7의 "cv가 다를 때만 CONFIG_SET"은 이 값이 있어야 성립한다. 3차에서
  Telemetry가 승인 전 차단되면 서버가 단말 `cv`를 알 길은 REGISTER뿐이다.
- SIM 또는 통신사에서 MSISDN을 제공하지 않으면 `msisdn`은 빈 문자열을 허용한다.
- 서버는 topic의 UUID와 payload의 `uuid`가 같은지 확인한다.
- 서버는 **단말 레코드를 topic의 UUID로 upsert**한다(2차, §4.1). REGISTER를
  놓쳐도 status로 레코드가 생긴다. REGISTER는 보강 정보다.

#### 모델과 버전을 여기에만 싣는 이유

`device_model`, `modem_model`, `imei`, `iccid`는 **런타임에 바뀌지 않는다.**
Telemetry에 매번 실으면 같은 문자열을 반복해서 보내게 된다.

단말은 **MQTT에 연결될 때마다 REGISTER를 다시 보낸다.** 펌웨어 갱신(USB 또는
OTA)은 반드시 재부팅을 거치므로 재연결과 REGISTER가 따라온다. 따라서 서버는
REGISTER만으로 항상 최신 모델/버전을 갖는다.

반대로 **서버가 보낸 값과 단말 실제가 어긋날 수 있는 세 가지**는 Telemetry에
매번 싣는다. 펌웨어 버전(`fw`), 스케줄 sequence(`ss`), CONFIG 버전(`cv`)이다.

### 1.1.5 PING / PONG

REGISTER 확인 후 서버는 해당 단말의 `device/{uuid}/cmd` topic으로 다음
메시지를 QoS 1로 발행한다.

```json
{"type":"PING","seq":1}
```

단말은 같은 `seq`와 자신의 UUID를 포함하여 `device/{uuid}/result` topic으로
응답한다.

```json
{"type":"PONG","seq":1,"uuid":"00112233445566778899AABB"}
```

`seq`는 **서버 전역 단조 증가** 32-bit unsigned integer다(2차 확정). topic과
무관하게 유일하므로 그룹 cmd와 개별 cmd의 `seq`가 충돌하지 않는다(5차 전제).
서버는 DB에 마지막 `seq`를 보관하고 재시작 후에도 이어 쓴다(§4.2
`server_state`).

서버는 수신한 PONG의 topic, UUID 및 `seq`가 전송한 PING과 모두 일치하는지
확인한다.

### 1.1.6 Telemetry **[1차]**

단말은 REGISTER 성공 직후 한 건을 보내고, 이후 설정된 주기로 반복한다.

```json
{"type":"TM","sq":41,"ts":"260924T2103","fw":"1.0.0","ss":15,"cv":3,
 "er":0,"on":1,"md":0,"pw":[70,64,64],
 "bv":2612,"bi":-150,"sc":87,"pp":3400,"li":230,"cs":3073}
```

한 줄로 보내며 실제 길이는 약 165바이트다.

> **`t` → `type` 는 2차 확정 사항이다.** 현재 1차 펌웨어는 `"t":"TM"` 을 보낸다.
> 2차에서 펌웨어(`lte_comm.c`)와 `Tools/sim/telemetry_sim.py`를 함께 고친다.
> 2차 전까지 서버 시험 도구는 두 키를 다 받아도 되지만, 2차 이후 서버 파서는
> `type`만 본다.

#### payload 규약 **[2차 확정]**

모든 메시지가 한 벌의 규약을 따른다. Event(§16.2), CMD(§3.10.7)도 같다.

| 항목 | 확정 |
|---|---|
| 메시지 종류 key | `type` 하나로 통일. Telemetry의 `"t":"TM"`도 `"type":"TM"`으로 |
| 시각 `ts` | `YYMMDDThhmm`으로 통일. **KST, 오프셋 없음** |
| 전압/전류 단위 | x100 정수. Event의 `batt_volt`도 `bv`로 |
| key 길이 | Event도 Telemetry와 같은 단축 key. AT 버퍼 384B 제약은 Event에도 적용된다 |

#### 항목

| key | 내용 | 단위 / 형식 |
|---|---|---|
| `type` | 메시지 종류. 항상 `"TM"` (1차 펌웨어는 `t`) | 문자열 |
| `sq` | 전송 일련번호 | 0부터 증가 |
| `ts` | 단말 RTC 시각 | `YYMMDDThhmm`, **KST, 오프셋 없음**, BCD 표기 그대로 |
| `fw` | 펌웨어 버전 | 문자열 |
| `ss` | 스케줄 sequence | 정수 |
| `cv` | CONFIG 버전 | 정수 |
| `er` | 오류 flag | 비트 정수, §16.2.2 |
| `on` | 점등 여부 | 0 / 1 |
| `md` | 운전 경로 | 0 스케줄 / 1 현장 수동 / 2 원격 |
| `pw` | PWM1(40W), PWM2(5W-1), PWM3(5W-2) | % 배열 |
| `bv` | 배터리 전압 | V x100 |
| `bi` | 배터리 전류 | A x100, **방전 시 음수** |
| `sc` | 배터리 잔량 | % |
| `pp` | PV 전력 | W x100 |
| `li` | 부하 전류 | A x100 |
| `cs` | 충전기 상태 | 비트필드, MPPT `0x3201` |

`bv`, `bi`, `sc`, `pp`, `li`, `cs`는 MPPT 보드에서 RS485 Modbus로 5초마다 읽은
값이며 단위와 배율은 PowerMPPT `spec/MODBUS_REGISTER_MAP.md`를 그대로 따른다.
`x100`은 **100으로 나누면 실제값**이라는 뜻이다. `2612`는 26.12V다.

#### `sq`로 유실과 재부팅을 함께 판정한다

`sq`는 전원 인가 시 0부터 시작한다.

| 관측 | 판정 |
|---|---|
| 번호가 건너뜀 | 그만큼 유실 |
| 번호가 **되돌아감** | 그 사이 재부팅 |

단말 가동 시간(uptime)을 따로 보내지 않는 이유가 이것이다. 같은 정보를 두 번
보낼 필요가 없다.

#### `cs`(충전기 상태)를 반드시 함께 봐야 한다

MPPT는 **값을 못 읽는 항목을 0으로 응답한다.** 응답 자체를 거르면 보드가 살아
있는데도 통신 두절로 오인되기 때문이다.

그래서 `pp`나 `bi`가 0인 것만으로는 세 가지를 구분할 수 없다.

| 실제 상황 | `cs` 로 구분 |
|---|---|
| 밤이라 발전 없음 | `D15-D14 = 00` 정상, `D0 Running = 0` |
| 패널/아답터 미연결 | `D15-D14 = 01` 무입력 |
| 충전 완료 | `D0 Running = 0`, `D3-D2 = 01` Float |
| 센서 통신 실패 | 단말 `er`의 `MPPT_OFFLINE` 비트 |

`cs` 비트 정의는 PowerMPPT `spec/MODBUS_REGISTER_MAP.md`의
`0x3201 충전기 상태 - 비트 정의`를 따른다.

#### 서버가 유의할 점

- **만충 부근에서 `bv`가 톱니로 보인다.** 충전기가 CV와 완료 사이를 1초 주기로
  오가며 배터리 전압이 약 1V 폭으로 진동한다. 그래프에 그릴 때 이동평균을
  거는 편이 낫다.
- **`sc`(잔량)는 추정값이다.** 전류 적산이 기본이라 장시간 만충이나 완방 없이
  유지되면 오차가 누적된다.
- **일 단위 발전량/소비량 집계는 서버가 한다.** MPPT 보드에 RTC가 없어 달력
  날짜를 모른다. 2차에서 단말이 금일 값을 올리더라도 자정 기준이 아니라
  부팅 후 24시간 주기다.

#### 주기

| 항목 | 값 |
|---|---|
| 공장 기본값 | 600초 (10분) |
| 허용 범위 | 60 ~ 3600초 (1 ~ 60분) |
| 변경 방법 | CONFIG의 `ti` |

**시험 단계에서는 10분을 쓰고, 운영 전환 시 30 ~ 60분으로 늘린다.**

주기별 데이터 사용량이다. 한 건 약 225바이트(AT 명령 포함) 기준이다.

| 주기 | 하루 | 월 |
|---|---|---|
| 10분 | 144건 / 37KB | 1.1MB |
| 30분 | 48건 / 12KB | 0.4MB |
| 60분 | 24건 / 6KB | 0.2MB |

#### 전송 실패 처리

단말은 **재시도하지 않는다.** 다음 주기에 새 값으로 다시 보내는 편이 낫고,
여기서 붙들고 있으면 PING 응답이 늦어진다. 실패해도 `sq`는 올려서 서버가
유실을 셀 수 있게 한다.

### 1.1.7 CONFIG **[2차]**

서버가 단말 설정을 맞추기 위해 주고받는 최소 항목이다.
**1차에서 2차로 이관을 확정했다.** 1차 펌웨어는 `config` topic을 구독하지 않으며,
1차 시험에서 서버는 `CONFIG_SET`을 발행하지 않는다.

연결 순서는 다음과 같다.

```text
단말 → REGISTER            (식별 + fw / ss / cv 현재값)
서버 → CONFIG_SET          (cv 가 다를 때만)
단말 → CONFIG_ACK
서버 → SCHEDULE_UPDATE     (ss 가 다를 때만, 6차)
단말 → ACK
        ↓
     Telemetry 시작
```

| 방향 | Topic | QoS |
|---|---|---|
| 서버 → 단말 | `iotlight/device/{uuid}/config` | 1 |
| 단말 → 서버 | `iotlight/device/{uuid}/result` | 1 |

#### CONFIG_SET

```json
{"type":"CONFIG_SET","cv":3,"ti":600,"lat":37.3617,"lon":126.9352}
```

| key | 내용 | 범위 | 단말 처리 |
|---|---|---|---|
| `cv` | CONFIG 버전 | 0 ~ 65535 | Flash 저장. Telemetry `cv`로 되돌려 보냄 |
| `ti` | Telemetry 주기(초) | 60 ~ 3600 | Flash 저장. 범위 밖이면 거부 |
| `lat` `lon` | 설치 좌표 | WGS84 십진수 | **보관만 한다.** 운전에 쓰지 않음 |

좌표를 단말에 두는 이유는 PC 설정 도구로 스케줄 표를 만들 때 쓴 좌표와 서버
지도가 어긋나면 현장을 찾을 수 없기 때문이다. 단말이 이 값으로 스케줄을
다시 만들지는 않는다.

`site`(장소명)는 서버 DB에 두면 되므로 단말에 내려보내지 않는다.

#### CONFIG_ACK

```json
{"type":"CONFIG_ACK","uuid":"...","cv":3,"result":"OK"}
```

| `result` | 의미 |
|---|---|
| `OK` | 전부 적용하고 Flash에 저장함 |
| `RANGE` | 범위를 벗어난 항목이 있어 적용하지 않음 |

거부한 경우 단말은 이전 값을 유지하고 `cv`도 올리지 않는다. 서버는 Telemetry의
`cv`가 자기가 보낸 값과 같아질 때까지 재전송한다. **재전송 간격은 다음
Telemetry 수신 시점이다.** 타이머를 따로 두지 않는다.

#### 2차 범위

**2차는 위 4개 항목(`cv`, `ti`, `lat`, `lon`)까지만 구현한다.** `grp`는 5차에
추가한다(§3.10.9). 아래는 6차 이후다.

- 저전압 임계값, 밝기, 스케줄 Offset 등 운전 설정의 서버 변경
- `SCHEDULE_UPDATE`로 372일 표 갱신
- `STATUS_GET` 즉시 조회
- OTA

2차까지 운전 설정은 **PC 설정 도구(`Tools/config_tool`)로만** 바꾼다.

#### 2차 구현 항목

| 쪽 | 할 일 |
|---|---|
| 펌웨어 | `device/{uuid}/config` 구독 추가 (구독 슬롯 2번째), JSON 파서, `system_data` 저장 |
| 펌웨어 | REGISTER에 `cv`, `ss`, `ti` 추가 (§1.1.4) |
| 서버 | Telemetry `cv`가 보낸 값과 같아질 때까지 재전송. 간격은 다음 Telemetry 수신 시점 |

**`cv`의 주인은 CONFIG_SET 하나다.** REGISTER_ACK(3차)에는 `state`, `site`만
싣고 `cv`, `grp`는 싣지 않는다(§3.3). retain 메시지에 설정값이 섞이면 재부팅
시 옛 값이 먼저 도착한다.

### 1.1.8 시험 순서 및 합격 기준

#### 1차-A 모뎀 접속 시험

```text
서버: Mosquitto 실행 및 TCP 1883 대기
   ↓
단말: LTE 망 등록 및 IP 할당
   ↓
단말: ID/PW를 사용하여 MQTT Broker 접속
   ↓
단말: *WMQTCON:2 수신
   ↓
서버: Broker 로그에서 UUID Client ID 확인
```

다음 조건을 모두 만족하면 1차-A 성공으로 판정한다.

1. 서버에서 Mosquitto가 TCP 1883으로 대기한다.
2. 단말 로그에 `*WMQTCON:2`와 `MQTT CONNECTED infontech.co.kr:1883`이 표시된다.
3. Broker 로그에서 단말의 24자리 UUID Client ID 연결을 확인한다.

이 단계에서는 웹 서버, DB, REGISTER 저장, PING/PONG 처리 기능이 없어도 된다.

#### 1차-B 메시지 왕복 시험

```text
서버: mqtt_test.py 실행 (iotlight/device/+/# 구독)
   ↓
단말: 재부팅 → MQTT Broker 접속
   ↓
단말: device/<uuid>/cmd 구독
   ↓
단말 → 서버: REGISTER
   ↓
서버 → 단말: PING
   ↓
단말 → 서버: PONG
```

**`mqtt_test.py`를 먼저 실행한 뒤 단말을 재부팅한다.** REGISTER는 (재)연결
시에만 오므로 순서를 바꾸면 120초 타임아웃으로 실패한다.

다음 조건을 모두 만족하면 1차-B 성공으로 판정한다.

1. 단말 로그에 MQTT 접속 및 구독 성공이 표시된다.
2. 서버가 유효한 REGISTER JSON을 수신한다.
3. topic UUID와 REGISTER UUID가 일치한다.
4. 서버가 PING을 QoS 1로 발행한다.
5. 서버가 같은 UUID와 `seq`의 PONG을 제한시간 안에 수신한다.

PC 간이 서버 도구는 SolarLTE 프로젝트의 `Tools/mqtt_test.py`를 사용한다.

```powershell
python Tools\mqtt_test.py --device-uuid 00112233445566778899AABB --timeout 120
```

#### 1차-C 주기 보고 확인

```text
단말: REGISTER 발행 직후 Telemetry 1건 발행
   ↓
서버: mosquitto_sub -t 'iotlight/device/+/status' 로 수신
```

다음을 확인한다. **1차 합격 판정 항목은 아니다.**

1. REGISTER 직후 Telemetry 1건이 도착한다.
2. 설정 주기(기본 600초)마다 Telemetry가 반복 도착한다.
3. `sq`가 1씩 증가한다.

CONFIG 왕복은 2차 합격 기준으로 옮겼다.

#### 2차 합격 기준

1. 단말별 계정으로 접속, 공용 계정 접속은 거부됨 (§1.1.2.2)
2. 다른 UUID topic에 발행 시도 → Broker가 거부 (ACL 확인)
3. register / status가 DB에 저장되고 `device.last_telemetry_at`이 갱신됨 (§4)
4. `CONFIG_SET`(`ti`=300) 발행 → `CONFIG_ACK result=OK` → 다음 Telemetry `cv`
   일치, 주기 300초로 변경
5. `ti`=10 발행 → `CONFIG_ACK result=RANGE`, `cv` 미변경

#### 현재 진행 상태 (2026-09-24)

단말은 준비되었고 **서버 Broker만 남았다.**

| 항목 | 상태 |
|---|---|
| LTE 망 등록 | 완료 |
| IP 할당 | 완료 (IPv6 단독, §1.1.9 참고) |
| MQTT 설정 및 접속 시도 | 정상 동작 |
| Broker 접속 결과 | `*WMQTCON:0` — 접속 실패 |
| 재시도 | 30초 주기로 정상 반복 |

`*WMQTCON:0`은 모뎀이 접속을 시도했지만 상대가 응답하지 않았다는 뜻이다.
`infontech.co.kr:1883`에 Mosquitto가 아직 없기 때문이며 단말 쪽 문제는 아니다.

남은 서버 작업은 다음 세 가지다.

1. Mosquitto 설치 및 TCP 1883 listener 기동
2. AWS Security Group과 OS 방화벽에서 TCP 1883 허용
3. `solarlte-test` / `solarlte-test-2026` 계정 등록

### 1.1.9 단말 IP 할당 형태

단말은 `AT*WWANIP?`로 IP를 확인하는데, **IPv4가 비어 있고 IPv6만 할당되는 것이
정상**이다. 국내 Cat.M1 망의 일반적인 동작이며 이전 양산 제품도 같았다.

MQTT는 WD-N522S 모뎀 내장 스택이 처리하므로 서버가 IPv6를 지원해야 하는 것은
아니다. 단말이 호스트명 `infontech.co.kr`을 그대로 넘기면 모뎀이 DNS를 해석하고
IPv4로 접속한다. **서버는 IPv4 전용으로 구성해도 된다.**

접속 경로는 `AT*RNDISDATA=1`을 먼저 시도하고, 모뎀이 지원하지 않아 `ERROR`가
오면 `AT*AUTOCONN=1`로 대체한다. 두 경우 모두 서버 구성에 영향을 주지 않는다.

## 1.2 MQTTS 전환 + 운영 Broker 분리 **[4차]**

현장 설치 가능 상태를 만든다. **이 단계 전에는 시험 단말 외에 설치하지 않는다.**

### 1.2.1 왜 4차인가

- 2·3차의 서버 로직은 전송에 무관하다. TLS를 먼저 하면 서버 일정이 모뎀 TLS
  조사(§0.4 P-1)에 걸린다.
- 진짜 신원 보증은 2차 단말별 계정이다(§1.1.2.2). TLS는 그 계정이 평문으로
  지나가는 것을 막는 층이다. 순서는 계정 → TLS가 맞다.
- LTE 무선 구간은 통신사가 암호화한다. 평문 노출 구간은 통신사 코어 → AWS
  사이 인터넷 구간이다(§0.3).

### 1.2.2 범위

| 항목 | 확정 |
|---|---|
| Broker | 시험 Broker(1883)와 운영 Broker(8883) 분리. 시험 Broker는 유지하되 운영 단말 계정을 두지 않는다 |
| 서버 인증서 | `infontech.co.kr` Let's Encrypt 또는 상용 인증서. 갱신 자동화 |
| 단말 | 루트 CA 저장, 서버 인증서 검증 ON, TLS 1.2. `LTE_MQTTS_INCLUDE` 정의 시 `LTE_MQTT_BROKER_PORT`=8883 (`lte_config.h`) |
| 클라이언트 인증서 | 쓰지 않는다. 단말 신원은 2차 계정으로 충분하고, 모뎀 인증서 관리 부담이 크다 |
| 서버 코드 | 접속 설정만 바뀌어야 한다. 그 이상 바뀌면 2·3차 설계가 전송에 의존한 것이다 |

### 1.2.3 모뎀 TLS 조사 결과에 따른 분기 (§0.4 P-1)

| 모뎀 TLS 지원 형태 | 대응 |
|---|---|
| 루트 CA 저장 + 서버 검증 가능 | 정상 경로. ISRG Root X1(LE) 또는 상용 CA 루트를 저장 |
| 암호화만 되고 검증 불가 | 임시 허용하되 본 사양서에 명시. 계정(2차)이 신원을 담당 |
| TLS 미지원 | 운영을 평문으로 갈 수 없다. VPN/APN 사설망 등 통신사 옵션 검토. 이 경우 3차 완료 시점에 결정 필요 |

### 1.2.4 합격 기준

1. 운영 Broker 8883 접속, 1883은 운영 계정 거부
2. 잘못된 인증서(자체 서명) 서버에 접속 시 단말이 거부
3. 3차 합격 시나리오 1~5(§3.9.1)를 운영 Broker에서 재통과
4. TLS 핸드셰이크 포함 재접속 1회당 데이터량 측정 → §1.1.6 월 사용량 표 갱신

## 2. 단말 등록 **[3차]**

Device UUID는 STM32G0B0 Unique ID 기반 값을 사용한다.

신규 단말:

```text
신규 접속
   ↓
PENDING
   ↓
관리자 확인
   ↓
설치 위치 / 그룹 / 장비정보 등록
   ↓
ACTIVE
```

기본 상태:

- PENDING
- ACTIVE
- SUSPENDED
- REJECTED
- RETIRED

2차에는 승인 게이트가 없으므로 DB의 `state`를 항상 `ACTIVE`로 저장한다(§4.2).

## 3. 단말 승인 및 정상 운용 전환 **[3차]**

**이 장은 전부 3차다.** 전송은 여전히 평문이다. 승인 로직은 TLS와 무관하므로
4차보다 먼저 만든다(§0.1). 1차 펌웨어에는 승인 게이트가 없다.
서버 쪽에서 미리 설계에 반영할 수 있도록 규격을 먼저 확정해 둔다.

관리자 화면은 **DB 플래그 편집 수준**이다. 미승인 단말 목록, 승인 버튼,
`site` / `lat` / `lon` 입력. 지도와 대시보드는 7차다.

신규 단말은 MQTT 연결에 성공하더라도 자동으로 정상 운용 상태로 전환하지 않는다.

### 3.1 전체 순서

```text
1. MQTT 연결 + cmd / config topic 구독
        ↓
2. 단말 → REGISTER            등록 요청
        ↓
3. 서버 → REGISTER_ACK        state = PENDING
        ↓
   ┌── 단말 대기. Telemetry 보내지 않음 ──┐
   │   조명은 자체 스케줄로 정상 운전      │
   └──────────────────────────────────────┘
        ↓
4. 관리자 확인 · 설치 위치 / 그룹 배정 · 승인
        ↓
5. 서버 → REGISTER_ACK        state = ACTIVE
        ↓
6. 서버 → CONFIG_SET → 단말 CONFIG_ACK
        ↓
7. 서버 → SCHEDULE_UPDATE → 단말 ACK   (필요 시, 6차)
        ↓
8. 단말 Telemetry 시작
```

### 3.2 REGISTER 가 승인보다 먼저인 이유

**단말이 아무것도 보내지 않으면 서버는 그 단말이 존재하는지 모른다.**
관리자 화면의 미등록 단말 목록에 띄울 근거가 없다.

`REGISTER`는 등록 **완료**가 아니라 등록 **요청**이다.
"저 여기 있습니다, UUID는 이것이고 모델은 이것입니다"를 먼저 보내야 관리자가
승인할 대상이 생긴다.

승인 게이트가 막는 것은 **REGISTER 이후의 모든 것**이다.
CONFIG, Schedule, Telemetry, 원격 제어가 전부 ACTIVE 이후에만 오간다.

### 3.3 REGISTER_ACK

| 방향 | Topic | QoS | Retain |
|---|---|---|---|
| 서버 → 단말 | `iotlight/device/{uuid}/config` | 1 | **1** |

**이 topic 만 retain 을 쓴다.** 단말이 승인 상태를 Flash 에 저장하지 않기
때문이다(§3.5). 재부팅하면 승인 여부를 잊으므로, 구독 직후 브로커가 마지막
상태를 즉시 내려줘야 관리자 조작 없이 ACTIVE 로 복귀한다.

retain 이 없으면 재부팅한 단말이 REGISTER 를 다시 보내고 서버가 응답해 줄
때까지 조명이 관제에서 빠진다. 서버가 잠깐 죽어 있으면 그 시간이 길어진다.

승인을 취소할 때는 `state` 를 바꾼 메시지를 다시 retain 으로 덮어쓴다.

빈 payload 를 retain 으로 보내면 브로커가 retain 을 지운다. 그 단말이 "영구
미승인" 이 되는 것이 아니라 **무응답 상태로 돌아가 30분 주기 REGISTER 재전송을
재개한다**(§3.4, §3.6). `RETIRED` 단말을 정리할 때 쓴다.

```json
{"type":"REGISTER_ACK","uuid":"...","state":"PENDING"}
{"type":"REGISTER_ACK","uuid":"...","state":"ACTIVE","site":"A-12"}
{"type":"REGISTER_ACK","uuid":"...","state":"REJECTED","reason":"unknown device"}
```

**`state`와 `site`만 싣는다.** `cv`, `grp`는 싣지 않는다. 설정값은 항상
`CONFIG_SET`으로만 내려간다(§1.1.7). retain 메시지에 설정값이 섞이면 재부팅
시 옛 값이 먼저 도착한다.

서버는 **REGISTER를 받을 때마다 반드시 응답한다.** retain 여부와 무관하며,
상태가 변하지 않았어도 응답한다. 단말이 응답을 못 받으면 서버가 살아 있는지 알 수 없어 계속 재전송한다.

### 3.4 상태별 단말 동작

| state | Telemetry | REGISTER 재전송 | 비고 |
|---|---|---|---|
| (무응답) | 보내지 않음 | O | 서버가 못 받았거나 재시작 |
| `PENDING` | 보내지 않음 | O (느리게) | 승인 대기 |
| `ACTIVE` | **보냄** | X | 정상 운용 |
| `SUSPENDED` | 보내지 않음 | X | 연결은 유지 |
| `REJECTED` / `RETIRED` | 보내지 않음 | X | 재전송도 중지 |

`SUSPENDED`는 서버가 일시 중지시킨 상태다. 연결을 끊지 않는 이유는 해제
명령을 받을 통로가 필요하기 때문이다.

### 3.5 승인 상태를 Flash에 저장하지 않는다

**단말은 승인 상태를 메모리에만 들고 있고 전원을 내리면 잊는다.**
MQTT 연결마다 REGISTER를 다시 보내고 서버가 매번 상태를 알려준다.

| | Flash 저장 안 함 (채택) | Flash 저장 |
|---|---|---|
| 승인 취소 반영 | 즉시 | 안 됨. 서버와 어긋남 |
| 단말 로직 | 단순 | 상태 동기화 필요 |
| 재부팅 후 | REGISTER 왕복 한 번 (수 초) | 바로 Telemetry |

재부팅 후 왕복 한 번은 몇 초다. 승인 취소가 단말에 반영되지 않는 위험이 그보다
크다고 보아 **저장하지 않는 쪽을 택했다.**

### 3.6 REGISTER 재전송 주기

서버가 재시작하면 세션 상태를 잃는다. 단말이 한 번만 보내고 말면 서버는 그
단말을 다시 찾지 못한다.

| 구간 | 주기 | 근거 |
|---|---|---|
| 처음 5회 | **5분** | 설치 직후. 관리자가 곧 승인한다 |
| 이후 | **30분** | 장기 방치. 망 사용량을 줄인다 |

MQTT 재연결이 일어나면 카운터를 처음으로 되돌린다. 재연결은 서버가 바뀌었을
가능성이 있는 시점이다.

### 3.7 승인과 무관하게 조명은 정상 운전한다

**가로등이 서버 승인을 못 받았다고 불이 꺼지면 제품이 아니다.**

승인 게이트가 막는 것은 서버 통신뿐이다. 아래는 승인 상태와 무관하게 그대로
동작한다.

- 372일 스케줄에 따른 점등 / 소등
- 다단계 밝기
- 배터리 저전압 차단 및 복귀
- DIP 스위치 현장 조작, OLED 설정 메뉴
- PC 설정 도구 연결

§1 기본 동작 원칙의 "LTE 또는 서버가 없어도 독립적으로 조명 운전이 가능해야
한다"와 같은 이야기다.

### 3.8 PENDING 상태에서 허용하는 것

| 허용 | 불가 |
|---|---|
| REGISTER 발행 | CONFIG 변경 |
| REGISTER_ACK 수신 | Schedule 배포 |
| PING / PONG | Telemetry |
| | LED 원격 제어 |
| | STATUS_GET |
| | OTA |

`PING / PONG`을 허용하는 이유는 연결이 살아 있는지 양쪽이 확인해야 하기
때문이다. 승인과 무관한 통신 경로 점검이다.

### 3.9 ACTIVE 승인 후 초기 동기화

```text
REGISTER 의 cv 와 서버 cv 비교          (§1.1.4)
   ↓
필요 시 CONFIG_SET → CONFIG_ACK
   ↓
Telemetry 시작
   ↓
Schedule Version 비교 / STATUS_GET      (6차)
```

3차에서는 Telemetry가 승인 전에 막히므로 서버가 단말 `cv`를 아는 경로는
REGISTER뿐이다. 그래서 REGISTER에 `cv`를 싣는다(2차, §1.1.4).

단말이 Telemetry에 싣는 `cv`(CONFIG 버전)와 `ss`(스케줄 sequence)로 서버가
동기화 완료를 확인한다(§1.1.6).

### 3.9.1 3차 합격 기준

1. 신규 단말 접속 → `PENDING` → Telemetry 없음, PING/PONG 됨
2. 관리자 승인 → `ACTIVE` → CONFIG_SET → Telemetry 시작
3. 단말 재부팅 → retain ACK로 관리자 조작 없이 `ACTIVE` 복귀
4. 서버 프로세스 재시작 → 단말 REGISTER 재전송으로 복구
5. `SUSPENDED` → Telemetry 중지, 연결 유지, 해제 시 재개

4차는 이 다섯을 운영 Broker에서 다시 통과해야 한다(§1.2.4).


## 3.10 그룹 제어 **[5차]**

"산본동 전체 소등" 같은 일괄 제어를 위한 구조다. **개별 → 그룹 → 전체 순으로
구현하고 각각 합격 후 다음으로 간다.** 사내 마을방송
(`D:\xWIFI_Radio`)의 `village_id` 설계를 가져오되 조명에 맞게 바꾼다.

### 3.10.1 세 계층

| 계층 | 가리키는 것 | 키 | 정하는 주체 |
|---|---|---|---|
| 전체 | 전 단말 | 없음 (`all`) | 고정 |
| 그룹 | **같은 명령을 받는 묶음** | `group_id` | 서버 배정 |
| 단말 | 그 기계 한 대 | `UUID` | 공장에서 자동 |

```text
iotlight/all/cmd                 전체
iotlight/group/<group_id>/cmd    그룹
iotlight/device/<uuid>/cmd       그 한 대
```

### 3.10.2 주소는 DB, 제어는 topic

**설치 주소, 담당자, 전화번호는 서버 DB에만 둔다.** topic에도 단말에도 넣지
않는다.

그래야 주소 표기가 바뀌거나 담당자가 바뀌어도 DB 한 줄만 고치면 되고 단말은
손대지 않는다. 개인정보가 브로커를 지나다니지 않는 효과도 같이 얻는다.

### 3.10.3 group_id 형식은 서버가 정한다

**단말은 이 값의 의미를 해석하지 않는다.** 받은 문자열을 topic에 그대로
끼워넣어 구독할 뿐이다. 그래서 형식은 서버가 정하면 되고, 나중에 바꿔도
펌웨어를 건드리지 않는다.

| | |
|---|---|
| 허용 | 숫자 8 ~ 16자리 |
| 미배정 | **전부 `0`** (자리수 무관). 이 값이면 그룹 topic을 구독하지 않는다 |
| 거절 | 숫자가 아니거나 범위 밖. 로그를 남기고 이전 값을 유지 |

미배정 판정은 특정 문자열 비교가 아니라 **"전부 0인가"** 로 한다.
`00000000`이든 `000000000000`이든 같게 다룬다.

topic에 들어가는 값이므로 `/`, `+`, `#`는 쓸 수 없다. 숫자만 쓰면 안전하다.

### 3.10.4 기본 제안: 법정동코드 기반 2계층

마을방송은 리 단위 방송이라 `법정동코드(10) + 연번(2)` 한 계층으로 충분했다.
가로등은 **동 전체**와 **공사 구간** 두 단위가 다 필요하다.

```text
4141011000          동 단위      법정동코드 10자리
4141011000 01       구역 단위    + 구역 연번 2자리
```

법정동코드는 **시도(2) + 시군구(3) + 읍면동(3) + 리(2)** = 10자리다.
도시는 리가 없어 마지막 2자리가 `00`이고, 그 상태로 동 단위가 된다.

| 운영 상황 | 발행 대상 |
|---|---|
| 산본동 전체 소등 | `iotlight/group/4141011000/cmd` |
| 산본로 공사 구간만 | `iotlight/group/414101100001/cmd` |
| 전국 일괄 | `iotlight/all/cmd` |
| 한 등만 | `iotlight/device/<uuid>/cmd` |

**단말은 자기가 속한 계층을 모두 구독한다.** 그래서 서버는 원하는 계층 하나에만
발행하면 된다. 서버가 topic 여러 개에 나눠 쓰지 않아도 된다.

위 코드값은 예시다. 실제 값은 주소 검색 API 응답에서 가져온다.

### 3.10.5 운영자에게 법정동코드를 직접 입력시키지 않는다

10자리 숫자를 손으로 치면 반드시 틀리고, 틀린 값은 **"명령이 안 간다"** 로만
나타나 원인을 찾기 어렵다.

등록 화면에서 **주소를 검색하면 법정동코드가 자동으로 채워지게** 한다.
구역 연번만 운영자가 고른다.

### 3.10.6 연번은 "단말 번호"가 아니라 "제어 그룹 번호"다

같은 구간의 가로등 10대에 `01` ~ `10`을 주면 구간 하나를 끄려고 서버가 topic
열 개에 발행해야 한다.

**같은 명령을 받아야 하는 것들은 같은 값을 준다.** 10대든 100대든 같다.
개별 지정은 UUID 경로가 이미 있으므로 그룹을 쪼갤 이유가 없다.

### 3.10.7 그룹 명령은 일시 override 다

**여기가 마을방송과 가장 다른 점이다.**

방송은 한 번 울리고 끝나지만 **조명은 상태가 남는다.** "산본동 전체 소등"을
보낸 뒤 서버가 죽거나 복구 명령을 못 보내면 그 동은 영영 어두운 채로 남는다.

그래서 그룹 명령에 **유효시간을 반드시 포함한다.**

**아래가 개별·그룹·전체 명령의 공통 포맷이다(2차 확정).** MCU 사양서 §18의
`LED_ON` / `Command ID` / `Expire` 체계는 폐기하고 이것으로 대체한다.

```json
{"type":"CMD","seq":12,"exp":30,"act":"off","dur":3600}
```

| key | 내용 | 비고 |
|---|---|---|
| `seq` | 서버 전역 일련번호 (§1.1.5) | 중복 실행 방지. topic과 무관하게 유일 |
| `exp` | 명령 유효시간(초) | 단말 RTC 기준 수신 지연이 이보다 크면 폐기. Clean Session=1이라 큐잉은 없지만 재전송 대비 |
| `act` | `off` 소등 / `on` 점등 / `pwm` 밝기 지정 / `auto` 즉시 스케줄 복귀 | |
| `dur` | override 유지시간(초) | 0 불가, 최대 86400 |
| `pwm` | `act=pwm` 일 때 0~100 | |

| 조건 | 단말 동작 |
|---|---|
| `dur` 경과 | **자동으로 스케줄 운전 복귀** |
| `dur` 누락 또는 0 | 명령을 거부하고 로그를 남긴다 |
| 재부팅 | override 를 잃고 스케줄 운전으로 시작 |
| `act=auto` | 즉시 복귀 |

override 를 Flash에 저장하지 않는 이유는 승인 상태와 같다(§3.5).
전원이 끊겼다 들어온 가로등이 꺼진 채로 있으면 안 된다.

최대 `dur` 은 24시간으로 제한한다. 그보다 오래 끄려면 스케줄을 바꾸는 것이 맞다.

### 3.10.8 우선순위

| 순위 | 경로 | 비고 |
|---|---|---|
| 1 | DIP3 강제 점등 | 현장 조작이 최우선 |
| 2 | 개별 UUID 명령 | 그룹보다 우선 |
| 3 | 그룹 명령 | `all` 보다 우선 |
| 4 | 전체(`all`) 명령 | |
| 5 | 스케줄 자동 운전 | 기본 |

같은 계층에서 나중에 온 명령이 앞의 것을 덮는다.

#### 계층별 override 슬롯

개별 / 그룹 / 전체 각각 **(값, 만료시각)을 따로 둔다.** 적용값은 유효한 슬롯 중
최상위다.

| 상황 | 동작 |
|---|---|
| 개별이 만료 | 아직 유효한 그룹 override 로 돌아간다 |
| 전부 만료 | 스케줄로 복귀 |
| 재부팅 | 전부 소거 |

Telemetry `md`로 현재 경로를 본다. 0 스케줄 / 1 현장 수동 / 2 원격.

**저전압 차단은 이 순위 밖이다.** 배터리를 보호해야 하므로 어떤 명령보다
우선한다(§12.5 MCU 사양서). 그룹 ON 명령을 받아도 저전압이면 켜지지 않는다.

### 3.10.9 단말이 group_id 를 받는 방법

`CONFIG_SET`에 실어 보낸다(§1.1.7). `REGISTER_ACK`에는 싣지 않는다(§3.3).

```json
{"type":"CONFIG_SET","cv":4,"ti":1800,
 "grp":["4141011000","414101100001"]}
```

`grp`는 **배열**이다. 단말은 받은 순서대로 구독한다. 서버가 계층을 하나만
쓰고 싶으면 원소 하나만 보내면 된다.

배열로 둔 이유는 §3.10.4의 2계층을 강제하지 않기 위해서다. 한 계층만 쓰려면
원소 하나만 보낸다.

**최대 2개다.** 아래 구독 한도 때문이다. 3개면 예비 슬롯이 없어진다.

### 3.10.10 구독 topic 한도가 설계를 제한한다

**WD-N522S 모뎀은 MQTT 구독 topic을 6개까지만 등록할 수 있다.**
(`AT*WMQTSUB`, AT Commands Guide v2.2 §7.1.6 "Topic 6 개까지 등록가능하다")

5차에서 다 채운 모습이다.

| # | topic | 용도 |
|---|---|---|
| 1 | `iotlight/device/<uuid>/cmd` | 개별 명령. `type` 으로 분기 |
| 2 | `iotlight/device/<uuid>/config` | 설정 · 승인 상태 (retained) |
| 3 | `iotlight/group/<grp[0]>/cmd` | 동 |
| 4 | `iotlight/group/<grp[1]>/cmd` | 구역 |
| 5 | `iotlight/all/cmd` | 전체 |
| 6 | — | 여유 1칸 |

**개별 명령을 payload 의 `type` 으로 분기시켜 `cmd` 하나로 모은 것이 여유를
만든다.** PING, 점·소등, 밝기 지정을 topic 으로 나누면 개별에만 세 칸을 쓰고
그룹까지 더한 순간 한도에 닿는다. 같은 이유로 응답도 `result` 하나로 모았다
(§1.1.3).

`grp` 는 최대 2개다(§3.10.9). 6번 슬롯은 예비로 남긴다. 스케줄 배포(6차)와
OTA(7차)는 새 topic을 쓰지 않고 `cmd` payload의 `type`으로 구분하므로 슬롯을
더 쓰지 않는다.

수신 메시지는 `*WMQTRCV:<topic>,"<message>"` 형태로 topic이 함께 오므로,
어느 계층에서 온 명령인지 단말이 구분할 수 있다.

> **1차가 구독하는 것은 `device/<uuid>/cmd` 하나다.** `config`는 2차, 나머지는 5차다.

### 3.10.11 그룹 명령에도 응답한다

그룹 명령을 받은 단말은 **각자 개별 topic으로 응답한다.**

```text
서버 → iotlight/group/4141011000/cmd    한 번 발행
단말 → iotlight/device/<uuid>/result    10대가 각각 응답
```

응답이 없으면 그 단말만 골라 개별 명령으로 재시도한다. 그룹 발행을 반복하면
이미 받은 단말까지 다시 처리한다.

```json
{"type":"CMD_ACK","uuid":"...","seq":12,"result":"OK","act":"off","dur":3600}
```

## 4. 서버가 관리할 Device 최소 정보 **[2차]**

### 4.1 최소 수집 서비스

2차에서 만든다. 화면은 없다.

- 언어/프레임워크: 서버 담당 선택. 기준은 "Broker 재시작 후 자동 재구독, DB
  저장 실패 시 로그".
- 구독: `iotlight/device/+/register`, `.../status`, `.../result`, `.../event`
- **단말 레코드는 topic의 UUID로 upsert**한다. REGISTER를 놓쳐도 status로
  레코드가 생긴다. REGISTER는 보강 정보다.
- 저장: register → `device` 갱신, status → `telemetry` raw 적재 +
  `device.last_*` 갱신
- `sq` 판정: 건너뜀 = 유실 카운트, 감소 = 재부팅 이벤트 기록 (§1.1.6)
- `cs` 비트 해석은 저장하지 말고 조회 시 해석한다 (MPPT 레지스터 맵 변경 대비)

### 4.2 DB 최소 컬럼 (2차 착수 시 생성)

`device`

| 컬럼 | 비고 |
|---|---|
| `uuid` PK | 24자리 대문자 |
| `state` | PENDING / ACTIVE / SUSPENDED / REJECTED / RETIRED. 2차는 항상 ACTIVE로 저장 |
| `mqtt_password_hash` | 2차 (§1.1.2.2) |
| `fw`, `device_model`, `modem_model`, `imei`, `iccid`, `msisdn` | REGISTER |
| `cv_device`, `ss_device`, `ti_device` | 단말 보고값 (REGISTER / Telemetry) |
| `cv_server`, `ti_server`, `lat`, `lon`, `site` | 서버 의도값. `cv_server != cv_device`면 CONFIG_SET 재전송 |
| `grp0`, `grp1` | 5차 |
| `last_register_at`, `last_telemetry_at`, `last_sq`, `online` | |
| `lost_count`, `reboot_count` | `sq` 판정 누적 |

`telemetry` — `uuid`, `received_at`, `ts_device`, `sq`, raw JSON 전체 컬럼.
해석은 조회 시.

`command` — `seq` PK(전역), `uuid` 또는 `group_id`, `type`, payload,
`sent_at`, `acked_at`, `result`.

`server_state` — `last_seq` (재시작 후 seq 이어쓰기, §1.1.5).

### 4.3 화면에 보이는 항목 (3차 이후)

Device 기본정보: UUID, Device Name, Firmware Version, Schedule Version,
Config Version, LED_BASE_RAW, 등록 상태, 설치 주소, Latitude, Longitude,
마지막 통신시간.

LTE / SIM: MSISDN, IMEI, ICCID (필수), LTE Signal, LTE 연결 상태 (상태).
Carrier는 필요할 경우만 추가한다.

## 5. Schedule 생성 기본 원칙 **[6차]**

서버와 MCU가 사용하는 최종 Schedule은 다음 항목으로 구성한다.

- 날짜별 시작시간과 종료시간 372개
- 시작 Offset과 종료 Offset
- 40W, 5W1, 5W2 수동 PWM 비율
- 시작 PWM 비율
- 절대시간 다중 4곳과 각 PWM 비율
- Package Version, Sequence, CRC32

날짜별 데이터에는 다중시간과 PWM 비율을 반복 저장하지 않는다.

---

## 6. Schedule 생성 입력 구조

### 6.1 날짜별 시간

서버는 위치정보 또는 관리자가 입력한 값으로 12개월 x 31일의 시작/종료 시간을 만든다.

```text
start_hour   : 0~23
start_minute : 0~59
stop_hour    : 0~23
stop_minute  : 0~59
day_count    : 372
```

존재하지 않는 날짜도 Table 위치를 유지하며 직전 유효값 또는 생성 정책값으로 채운다.

### 6.2 Offset

```text
start_offset_minute : -60~+60
stop_offset_minute  : -60~+60
```

Offset은 시작과 종료에만 적용한다. 다중시간에는 적용하지 않는다.

### 6.3 PWM

```text
manual_40w_percent : 10~99
manual_5w1_percent : 10~99
manual_5w2_percent : 10~99
start_pwm_percent  : 0~100
```

### 6.4 다중시간

다중시간 네 곳은 모든 날짜에 공통인 절대시간이다.

```text
stage[0].hour / minute / pwm_percent
stage[1].hour / minute / pwm_percent
stage[2].hour / minute / pwm_percent
stage[3].hour / minute / pwm_percent
```

시간은 BCD가 아닌 일반 10진수이며 시는 0~23, 분은 0~59다. 예를 들어 오후
8시 30분은 `hour = 20`, `minute = 30`이다. PWM 비율은 0~100%다.

## 7. Schedule 계산 규칙

```text
적용 시작 = 날짜별 시작 + 시작 Offset
적용 종료 = 날짜별 종료 + 종료 Offset
```

Offset과 다중시간이 충돌하면 MCU와 서버 Preview 모두 다음 규칙을 사용한다.

```text
적용 시작 >= 다중1 → 적용 시작 = 다중1
적용 종료 <= 다중4 → 적용 종료 = 다중4
```

최종 순서는 다음 조건을 만족해야 한다.

```text
적용 시작 <= 다중1 < 다중2 < 다중3 < 다중4 <= 적용 종료
```

RTC 날짜가 바뀌면 새 날짜의 시작/종료 데이터를 즉시 사용한다. 1월 2일 02:00은
1월 2일 Table을 기준으로 자정 통과 구간을 계산한다.

PWM은 각 채널마다 한 번만 계산한다.

```text
최종 PWM = (수동 PWM x 현재 단계 비율 + 50) / 100
```

## 8. 단말 전송용 Schedule 구조

Binary Payload는 MCU의 little-endian 저장 구조와 동일한 고정 크기 포맷을 사용한다.

```c
typedef struct {
    uint8_t start_hour;
    uint8_t start_minute;
    uint8_t stop_hour;
    uint8_t stop_minute;
} SCHEDULE_DAY_t;

typedef struct {
    uint8_t hour;
    uint8_t minute;
    uint8_t pwm_percent;
    uint8_t reserved;
} SCHEDULE_STAGE_t;

typedef struct {
    int8_t start_offset_minute;
    int8_t stop_offset_minute;
    uint8_t manual_40w_percent;
    uint8_t manual_5w1_percent;
    uint8_t manual_5w2_percent;
    uint8_t start_pwm_percent;
    uint8_t reserved[2];
    SCHEDULE_STAGE_t stage[4];
} SCHEDULE_CONFIG_t;

typedef struct {
    uint32_t magic;
    uint16_t version;
    uint16_t year;
    uint16_t payload_size;
    uint16_t day_count;
    uint32_t sequence;
    uint32_t crc32;
    uint32_t reserved;
} SCHEDULE_HEADER_t;
```

크기:

```text
Header                   24 Byte
Config                   24 Byte
Day Table     372 x 4 = 1,488 Byte
----------------------------------
전체                   1,536 Byte
```

필드 Offset과 크기는 서버와 MCU에서 자동 시험으로 확인해야 하며 C 구조체 padding에
의존해 임의 직렬화하지 않는다.

## 9. Schedule Package 관리 **[6차]**

고정값:

```text
Magic        : 0x53434832
Version      : 2
Payload Size : 1512
Day Count    : 372
Package Size : 1536
```

CRC32는 Header의 `crc32` 필드를 0으로 놓고 전체 1,536 Byte에 대해 계산한다.
Sequence는 서버 또는 단말에서 새 Package를 확정할 때 증가한다.

단말은 Bank A/B 중 CRC가 정상이고 Sequence가 큰 Package를 사용한다. 전송이나 Flash
저장에 실패하면 기존 정상 Bank를 유지한다.

## 10. 서버 검증 항목

- 월/일 Table 위치와 전체 372개 확인
- 시작/종료 및 다중시간의 시 0~23, 분 0~59
- Offset -60~+60분
- 수동 PWM 10~99%
- 시작 및 다중 PWM 0~100%
- 다중시간 순서와 24시간 이내 운전범위
- Payload Size, Version, CRC32
- 생성 Year와 Schedule Version

하나라도 잘못되면 Package를 배포하지 않는다.

## 13. Schedule 배포 **[6차]**

```text
1. Header 및 Payload 생성
2. 서버 범위검사
3. CRC32 생성
4. cmd topic 으로 chunk 전송
5. 단말 조립 후 CRC 확인
6. 비활성 Flash Bank 저장
7. Flash 재검증 및 Active Bank 전환
8. 단말 ACK (result topic)
```

| 항목 | 확정 |
|---|---|
| 전송 topic | `iotlight/device/{uuid}/cmd`. 새 topic을 쓰지 않는다(§0.2) |
| ACK topic | `iotlight/device/{uuid}/result` |
| chunk 포맷 | `{"type":"SCH","seq":..,"idx":n,"tot":N,"d":"<base64>"}` |
| chunk 크기 | 모뎀 수신 버퍼(§0.4 P-3)로 결정 |
| 검증 | 조립 완료 후 CRC 검증 → Bank 저장 → `result`로 ACK |

1,536B 패키지가 대상이다(MCU 사양서 §4.4). 재전송 정책은 P-3 결과 후 확정한다.

## 15. 현장 수동 PWM과 서버 동기화

현장 엔코더에서 PB12로 저장하면 수동 PWM 값만 변경한 새 Sequence를 A/B Flash에
저장한다. DIP1은 40W, DIP2는 5W 두 채널을 설정한다.

서버가 이후 전체 Package를 내려보내면 서버 값이 최종값이 된다. 단말은 현장 변경값과
현재 Sequence를 상태정보로 서버에 보고하여 관제 값과 실제 장비 값이 다르지 않게 한다.


## 16. MQTT 연결 / Event / Telemetry / STATUS 운용

절마다 단계가 다르다. Telemetry(§16.3)는 1차, 연결 상태/LWT(§16.1)와
TELEMETRY_INTERVAL 전달 시점(§16.5)은 3차, Event와 STATUS_GET(§16.2, §16.4)은
6차다. TLS 전환은 §1.2(4차)다.

### 16.1 연결 상태와 LWT **[3차]**

연결 상태는 Telemetry 수신 주기와 별도로 관리한다. **Online / Offline 은 LWT
기반이다.**

| 항목 | 값 |
|---|---|
| LWT topic | `iotlight/device/{uuid}/event` |
| LWT payload | `{"type":"LWT","uuid":"..."}` |
| QoS | 1 |
| ONLINE 판정 | Broker CONNECT 성공 시 서버가 ONLINE 처리 |
| OFFLINE 판정 | Broker 가 LWT 를 발행하면 OFFLINE |

모뎀 LWT 지원 여부는 §0.4 P-2 조사 결과에 따른다. **미지원이면 Telemetry
주기 × 3 무수신 = OFFLINE 으로 대체한다.**

- CONNECT / Session 상태
- LWT
- Online / Offline

UI에서도 가능하면 다음을 구분한다.

```text
MQTT 상태        ONLINE
마지막 Telemetry  18분 전
```

### 16.2 Event **[6차]**

중요 상태 변화는 Event로 즉시 수신한다.

초기 대상 예:

- LED_BASE_RAW_CHANGED
- Config 변경
- Schedule 적용 결과
- 주요 Alarm
- Reset 관련 상태

Event는 기본 QoS 1을 사용한다.

#### 16.2.1 ERROR_CHANGE

단말은 "왜 점등되지 않는가"에 해당하는 상태를 한 벌의 bit flag로 관리하고
**값이 변할 때만** Event를 올린다. 같은 상태를 주기적으로 반복 전송하지 않는다.

| 항목 | 값 |
|---|---|
| Topic | `iotlight/device/{uuid}/event` |
| QoS | 1 |
| 조건 | flag 변화 시 1회 |

```json
{"type":"EV","ev":"ERR","uuid":"3A0031000B51383438393735",
 "er":17,"ep":16,"bv":2480,"ts":"260924T2103"}
```

payload 규약은 Telemetry 와 같다(§1.1.6 payload 규약, 2차 확정). AT 버퍼 384B
제약이 Event 에도 걸리므로 긴 key 를 쓰지 않는다.

| 필드 | 내용 |
|---|---|
| `type` | `EV` |
| `ev` | `ERR` (오류 flag 변화). 다른 Event 는 값을 늘린다 |
| `er` | 현재 flag, 정수 (Telemetry `er` 와 같다) |
| `ep` | 직전 flag, 서버가 SET/CLR을 구분할 수 있다 |
| `bv` | 배터리 전압 V x100, `BATT_LOW` 판단 근거 |
| `ts` | 단말 RTC, `YYMMDDThhmm`, KST 오프셋 없음 |

사람이 읽을 이름 배열은 싣지 않는다. 서버가 §16.2.2 표로 풀어 쓴다.

#### 16.2.2 error_flags bit 정의

단말 `APP_ERR_e`와 같으며 bit 순서가 표시 우선순위다. 앞쪽이 LED 구동을 직접
막는 원인이다.

| bit | 이름 | 의미 | 점등 차단 |
|---:|---|---|---|
| 0x0001 | `BATT_LOW` | 배터리 저전압 차단 | O |
| 0x0002 | `RTC_INVALID` | 시각 미확보, 스케줄 판정 불가 | O |
| 0x0004 | `LED_FAULT_M` | LED 드라이버 Master Fault | 예약 |
| 0x0008 | `LED_FAULT_S` | LED 드라이버 Slave Fault | 예약 |
| 0x0010 | `MPPT_OFFLINE` | MPPT 무응답, 저전압 보호 불가 | X |
| 0x0020 | `SCHEDULE_BAD` | Flash 불량, 기본 스케줄 사용중 | X |
| 0x0040 | `LTE_OFFLINE` | MQTT 미연결 | X |

`LTE_OFFLINE`은 서버에 도달할 수 없는 상태이므로 Event로 올라오지 않는다.
연결이 복구된 뒤 `er`에 담겨 전달된다. 서버는 이 bit를 단독 판정에
쓰지 않고 `DEVICE_OFFLINE` 판정으로 대신한다.

`LED_FAULT_M/S`는 단말 회로 확정 후 사용한다. 서버는 bit를 미리 인식해 두고
값이 0인 상태로 처리한다.

#### 16.2.3 서버 처리 원칙

- 같은 flag가 반복 수신되면 중복으로 보고 Alarm을 다시 만들지 않는다.
- 단말 재부팅 후 첫 Telemetry의 `er`를 현재 상태로 신뢰한다.
  `ep`가 없거나 0이어도 재부팅 직후일 수 있다.
- flag가 0으로 바뀌면 해당 Alarm을 해제한다. 단말은 별도의 해제 Event를
  만들지 않는다.

### 16.3 Telemetry **[1차]**

Telemetry는 빠른 주기가 필요하지 않으며 기본적으로 다음 범위를 사용한다.

```text
10분 ~ 30분 또는 그 이상
```

주기는 서버 Config의 `TELEMETRY_INTERVAL`로 관리한다.

일반 Telemetry는 기본 QoS 0을 사용한다.

### 16.4 STATUS_GET **[6차]**

관리자가 즉시 최신 상태를 확인해야 할 경우 서버는 `STATUS_GET`을 전송한다.

단말 상세화면의 새로고침 등에서 사용할 수 있다.

응답 대상:

- UUID
- Firmware Version
- Schedule Version
- Config Version
- RTC
- Solar
- Battery
- Charger
- LED
- LED Current
- LED_BASE_RAW
- LTE Signal
- 현재 Mode

### 16.5 TELEMETRY_INTERVAL 전달 시점 **[3차]**

`TELEMETRY_INTERVAL`(CONFIG `ti`)은 단말 승인 전에는 전달하지 않는다.
2차에는 승인 게이트가 없으므로 REGISTER 직후 바로 전달한다.

```text
PENDING
→ 단말 Factory Default 사용

ACTIVE 승인
→ Config Version 확인
→ 필요 시 CONFIG_SET
→ TELEMETRY_INTERVAL 적용
```

운영 중 서버에서 Telemetry 주기를 변경하면 재접속을 기다리지 않고 즉시 `CONFIG_SET`을 전송한다.

단말은 정상 적용된 값을 Flash에 저장한다.


## 17. 원격 LED 제어 **[5차]**

명령 포맷은 §3.10.7 의 `CMD` 하나다. 개별·그룹·전체가 같은 payload 를 쓰며
topic 만 다르다(§3.10.1). 개별 → 그룹 → 전체 순으로 구현하고 각각 합격 후
다음으로 간다.

| `act` | 동작 |
|---|---|
| `on` | 강제 점등. `dur` 동안 유지 |
| `off` | 강제 소등. `dur` 동안 유지 |
| `pwm` | 밝기 지정 0 ~ 100 %. `dur` 동안 유지 |
| `auto` | 즉시 스케줄 복귀 |

`exp`, `dur` 은 필수다. `dur` 이 끝나면 슬롯 규칙(§3.10.8)에 따라 복귀한다.
응답은 `result` 의 `CMD_ACK`(§3.10.11) 다.

저전압 임계값, 밝기 기준값 등 운전 설정의 서버 변경은 6차에 CONFIG_SET 항목을
늘려서 한다.
