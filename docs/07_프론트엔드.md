# 07. 프론트엔드 (개발용 최소 화면)

- 작성일: 2026-09-25 / 갱신: 2026-09-26 (API 개정 반영 — 승인·프로필·HMAC, 사양서 §3.9.2 화면 1·2)
- 코드: `frontend/`. 실행법은 `frontend/README.md`.

## 목적

REST API(`docs/05`)가 실제로 무엇을 돌려주는지 사람이 눈으로 확인하고, 3차 최소 관리자 화면(사양서 §3.9.2:
단말 목록 / 승인·설정)을 **개발용**으로 돌리는 화면. 디자인·지도·차트·인증 없음.
Vite + React + TypeScript, UI 라이브러리 없이 `fetch` 만 쓴다. 운영 화면은 7차, 인증은 4차 전.

## 구조

```
frontend/
  vite.config.ts        dev 프록시: /api, /health → http://localhost:8000 (포트 5173)
  src/api.ts            REST 호출·타입(DeviceOut, Profile, Health 등)·에러 파싱 — docs/05 와 1:1
  src/format.ts         단위 변환(x100), er 비트, 상대시간, 이벤트 payload 요약(eventSummary)
  src/App.tsx           요약바 + 탭(#devices / #profiles / #system) + 좌우 분할(master-detail)
  src/DeviceList.tsx    왼쪽 단말 목록 (화면 1)
  src/DeviceDetail.tsx  오른쪽 승인 패널·설정 패널·상세·PING·삭제·이력 (화면 2)
  src/Profiles.tsx      프로필 탭 (표 안에서 편집)
  src/System.tsx        시스템 탭 (/health, /api/metrics 원본 JSON)
```

파일 탐색기처럼 **왼쪽 목록에서 고르면 오른쪽에 상세**. 라우팅은 `location.hash` 만. 10초마다 자동 갱신.

## 화면

| 영역 | 내용 | API |
|---|---|---|
| 요약바 | **승인 대기 N**(노란 배지), 전체/온라인/오프라인, state 별 수 — 목록 API 의 `counts` 로 한 번에. health: mqtt·db·`broker_log_tail`·`hmac_keys`·dropped, `test_account_enabled=true` 면 빨간 "공용 시험계정 열림" | `GET /api/devices?size=1` (counts), `GET /health` |
| 단말 목록 (화면 1) | UUID, 상태, 장소, F/W, 마지막 수신(`last_seen_at`), Online(`is_online` ●/○, tooltip 에 브로커 `online`), 프로필, **ti 의도/보고**, **ka 의도/보고**(`*_effective` vs `*_device`, 다르면 빨강), bv/sc(`last_telemetry`). 필터 state / online / 텍스트 `q` 전부 서버. PENDING 행 노란 배경(서버가 PENDING 먼저 정렬) | `GET /api/devices` |
| 승인 패널 (화면 2) | state 배지, `state_reason`, `state_changed_at`, 마지막 REGISTER_ACK 발행 시각. 버튼은 docs/05 전이표대로 현재 state 별: 승인(ACTIVE, site 비어 있으면 prompt, 24자) / 거부(REJECTED, reason 필수) / 일시 중지 / 해제 / 폐기(confirm) / 재검토·승인 취소(PENDING). `REGISTER_ACK 재발행` 버튼 | `PATCH …/state`, `POST …/register-ack` |
| "발행함 / 단말이 받음" | 버튼 뒤 두 줄. 발행함 = `register_ack_at`. 단말이 받음: ACTIVE 는 `last_telemetry_at > register_ack_at` 이면 "받음"(첫 Telemetry), 아니면 "대기 중 — 다음 단말 송신(최대 5분) 후". 그 외 state 는 `last_seen_at` 기준 참고 표시(직접 ACK 없음). RETIRED 는 빈 retain 안내. `published=false` 면 브로커 미연결 안내. 대기 중엔 5초마다 상세 폴링, 10분까지 | `GET …/{uuid}` |
| 설정 패널 | cv server/device + `config_pending` 이면 "CONFIG 미반영: cv_server X / cv_device Y", ti·ka 의도/보고, `config_mismatch`. 폼: 프로필 `<select>`, `ti_override`/`ka_override`(빈칸 = 프로필 값, 옆에 적용값), lat/lon, site(24자), address, bjd_code. **바뀐 필드만** PATCH. 응답 `published` 표시, false + `NOT_ACTIVE` 면 "승인 후 첫 Telemetry 때 전송됨". 단말 쪽 값이 바뀐 경우 CONFIG_ACK 이벤트를 5초 폴링(10분)해 결과 표시, 또는 `cv_device == cv_server` 되면 "받음" | `PATCH …/config`, `GET /api/profiles`, `GET …/events?kind=CONFIG_ACK` |
| 상세 | 기본정보 / LTE·SIM / 연결 상태 / 마지막 텔레메트리(단위 변환·er 비트·md 라벨) | `GET …/{uuid}` |
| PING · 삭제 | PING → PONG 이벤트 2초 폴링, **60초** 대기(서버→단말 지연 수십 초 정상). 삭제(confirm) | `POST …/ping`, `GET …/events?kind=PONG`, `DELETE …` |
| 이력 | 최근 텔레메트리 50건(cv 열 추가), 이벤트 50건 — kind 별 요약(REGISTER_ACK / STATE_CHANGE / CONFIG_SET / CONFIG_ACK / ONLINE / OFFLINE …) + 원본 JSON | `GET …/telemetry`, `GET …/events` |
| 프로필 탭 | id·name·ti·ka·단말 수 표, 행 안에서 편집 → 저장(바뀐 필드만 PATCH). ti/ka 를 바꾸면 `bumped_devices` 로 "N대에 다음 송신 때 CONFIG 전송". 추가 폼. 삭제(409 `PROFILE_IN_USE` 그대로 표시, id 1 비활성) | `/api/profiles` CRUD |
| 시스템 탭 | `/health`, `/api/metrics` 원본 JSON, 10초 갱신 | `GET /health`, `GET /api/metrics` |

오류는 `{error:{code,message,detail}}` 를 그대로 빨간 줄로 보여준다. REGISTER 전 단말은 대부분 null 이라 `-`.

## 왜 "발행함"과 "단말이 받음"을 따로 보이나

사양서 §1.1.10: 단말은 LTE NAT 뒤라 서버가 보낸 것은 **단말이 다음에 송신한 직후**에야 도착한다(최대 ti 약 5분).
승인(REGISTER_ACK retain)은 단말의 첫 Telemetry 로, CONFIG 는 CONFIG_ACK 와 Telemetry `cv` 로 확인한다.
화면은 서버가 발행한 시각과 단말이 실제로 받았다는 증거를 같은 줄에 섞지 않는다.

## 삭제된 것

- 계정 CSV import 탭 — ADR-003(HMAC 인증)으로 단말 계정 파일이 없어져 올릴 것이 없다. `POST /api/devices/import-accounts` 호출 코드 제거.
- 요약바의 "전체 목록 500개씩 다 읽기" — 목록 API 의 `counts` 로 대체(요청 1회).

## docs/05 에 없어서 가정한 것 (백엔드와 맞출 것)

- `counts` 는 필터(`state`/`online`/`q`)와 무관하게 **전체 기준**이라고 가정하고 요약바에 쓴다. 필터 기준이면 요약바는 `size=1` 무필터 요청이라 그대로 맞다.
- `PATCH …/config` 응답의 `published=false` 사유 필드명을 `reason` 으로 가정(`"NOT_ACTIVE"`). 문서 본문의 "reason="NOT_ACTIVE"" 표기를 따름.
- `PATCH …/profiles/{id}` 응답 = `ProfileOut + bumped_devices` 로 가정.
- `POST …/register-ack` 응답 형태 미기재 → JSON 그대로 보여준다.
- 이벤트 payload 의 키(STATE_CHANGE 의 `from`/`to`, CONFIG_ACK 의 `result` 등)는 docs/03 에 없어 몇 가지 후보 키를 찾아 요약하고, 없으면 원본 JSON 을 그대로 쓴다.
- `DeviceOut` 은 docs/03 `device` 컬럼 전부라 했으므로 `state_changed_at`, `online_changed_at`, `ka_device`, `grp`, `address`, `bjd_code`, `last_telemetry` 를 타입에 넣었다. 예전 `has_mqtt_account`, `ti_server`, `grp0/grp1` 은 뺐다.
