# 04. 인프라·운영

- 작성일: 2026-09-25 (2026-09-26 브로커 이미지 go-auth 전환 — ADR-003/004 반영, 2026-09-27 5차 권한 헤더·4차 TLS/브로커 분리 준비 — ADR-005/006)
- 영역: `infra/`, `docker-compose.yml`, `scripts/` (개발계획 §3)
- 원칙: **개발자는 운영 서버에 직접 접근하지 않는다.** 여기 적힌 명령은 담당자가 서버에서 실행한다. 그래서 모든 절차는 "복사해서 그대로 붙여 넣으면 끝"이 되게 적는다.
- 실제 호스트 IP, SSH 키, 비밀번호는 이 문서에 적지 않는다.

## 1. 구성 한눈에

```
단말 (LTE, WD-N522S) ──1883 평문(1차~3차) / 8883 TLS(4차~)──▶ ┌──────────── EC2 t3.small ────────────┐
PC 시험 도구 ─────────1883──────────────────────────────────▶ │ mosquitto ◀─1883(컨테이너망)─ backend │
                                                              │     │ mqtt-dynamic 볼륨 ▲      │       │
                                                              │     └─ passwd/acl 설치 ─┘   postgres  │
                                                              └───────────────────────────────────────┘
```

| 서비스 | 컨테이너 | 역할 | 외부 공개 |
|---|---|---|---|
| `mosquitto` | `iotlight-mosquitto` | 브로커 (`iegomez/mosquitto-go-auth`). files 계정(server·공용) + 단말 인증은 backend 에 HTTP 로 위임, retained REGISTER_ACK 보존, 접속 로그 파일 | 1883 (1차~3차, SG 로 IP 제한), 8883 (4차) |
| `backend` | `iotlight-backend` | FastAPI + aiomqtt 수집·제어 (2차~) + 단말 인증 API `/internal/mqtt/*` + 브로커 로그 tail | 없음 (3차 관리 화면 때 nginx 추가). `/internal/*` 는 컨테이너망 전용 |
| `postgres` | `iotlight-postgres` | PostgreSQL 16, `local-db` 프로파일 | 없음 |
| `web` | `iotlight-web` | nginx: 관리 화면 정적 + `/api`·`/health` 프록시, Basic auth, 사용자명 → `X-Remote-User` | 80 (4차: 443 + 80 리다이렉트) |
| `mosquitto-test` | `iotlight-mosquitto-test` | **4차 오버라이드에서만.** 시험 브로커(`eclipse-mosquitto:2`, `solarlte-test` 하나) | 1883 (SG 로 IP 제한) |
| `certbot` | `iotlight-certbot` | `certbot` 프로파일, 1회성. Let's Encrypt 발급·갱신(`--webroot`) | 없음 |

### 1.1 브로커 이미지: `iegomez/mosquitto-go-auth` (2026-09-26, ADR-003)

단말 비밀번호가 `HMAC-SHA256(K, UUID)` 계산값으로 바뀌었다(사양서 §1.1.2.2). 새 단말은 REGISTER 뒤에야 UUID 를 알므로 `password_file` 에 미리 넣을 수 없고, 접속 순간 계산해 비교해야 한다. 그래서 `eclipse-mosquitto:2` 대신 Mosquitto 2.0.15 + go-auth 플러그인 이미지를 쓴다. 이미지 안 사용자 `mosquitto` 는 **uid 1000** 이다(eclipse 는 1883 — 인증서 키 권한 root:1000 0640, §6.0 참고).

`infra/mosquitto/config/mosquitto.conf` 의 플러그인 블록:

| 옵션 | 값 | 뜻 |
|---|---|---|
| `plugin` | `/mosquitto/go-auth.so` | |
| `auth_opt_backends` | `files, http` | 순서대로 시도, 하나라도 허용하면 통과 |
| `auth_opt_hasher` | `pbkdf2` | files passwd 해시 (`pw` 기본값과 같다) |
| `auth_opt_files_password_path` / `auth_opt_files_acl_path` | `/mosquitto/data/passwd`, `/mosquitto/data/aclfile` | files 계정 = `server`, (1차) `solarlte-test`. **`pattern` 줄 없음** — 단말 ACL 은 http |
| `auth_opt_http_host` / `_port` | `backend` / `8000` | 컨테이너망 서비스명 |
| `auth_opt_http_getuser_uri` / `_aclcheck_uri` / `_superuser_uri` | `/internal/mqtt/auth` / `/acl` / `/superuser` | docs/05 "브로커 인증" |
| `auth_opt_http_params_mode` / `_response_mode` | `json` / `status` | 요청은 JSON body, 응답은 HTTP 상태(200 허용, 그 외 거부) |
| `auth_opt_http_timeout` | `5` | 초 |
| `auth_opt_disable_superuser` | `true` | superuser 검사 자체를 끈다(안 쓰는 HTTP 호출 1개 제거) |
| `auth_opt_cache` / `_cache_type` | `true` / `go-cache` | 프로세스 내 캐시 |
| `auth_opt_auth_cache_seconds` / `_acl_cache_seconds` | `600` / `600` | 인증·ACL 결과 기억. 1만 대 재접속 폭주 때 HTTP 호출 억제 |
| `auth_opt_auth_jitter_seconds` / `_acl_jitter_seconds` | `30` / `30` | 만료 시각 분산 |
| `auth_opt_log_level` | `info` | |

go-auth 가 backend 에 보내는 body(실측): auth `{"username","password","clientid"}`, acl `{"username","clientid","topic","acc"}` (`acc` 1 read, 2 write, 4 subscribe). superuser 는 `{"username"}` 뿐 — 지금은 꺼져 있다. 헤더는 `User-Agent: mosquitto-2.0.15`, `Content-Type: application/json` 뿐이라 사용자 정의 헤더(`X-Auth-Secret`)는 못 보낸다. files 에 없는 username(예: 틀린 비밀번호의 `server`)도 http 로 넘어오므로 backend 는 UUID 형식이 아니면 403 으로 답하면 된다.

**`depends_on: backend` 는 걸지 않는다**(backend 가 mosquitto 에 의존). go-auth 는 접속마다 HTTP 를 시도하므로 backend 가 늦게 떠도 그 뒤 접속부터 정상이다.

**go-auth 는 SIGHUP 으로 passwd/aclfile 을 다시 읽지 않는다** — 플러그인의 `mosquitto_auth_security_init(reload)` 가 빈 함수다(소스·실측 2026-09-26). files 계정이 바뀌면 브로커 재시작이 필요하다. §5 참고.

호스트 bind: `infra/mosquitto/config`(:ro), `infra/mosquitto/entrypoint.sh`(:ro), `infra/certs`(:ro, 4차 전엔 빈 디렉터리).

마을방송(aircast)과 다른 점: Icecast·nginx·TTS·파일 볼륨이 없다. 단말 식별은 MAC 이 아니라 24자리 UUID. topic root `iotlight`.

### 2.1 Security Group 규칙

| 방향 | 포트 | 소스 | 단계 | 비고 |
|---|---:|---|---|---|
| 인바운드 | 22/TCP | 관리자 IP 만 | 항상 | |
| 인바운드 | **1883/TCP** | **시험 접속원 IP 만** | 항상 | 시험 단말이 붙는 통신사(Cat.M1) NAT 출구 대역 + 시험 PC 공인 IP. 사양서 §0.3 "시험 Broker + 접속원 IP 제한 상태에서만". 4차 이후에도 유지 — 그때부터는 운영 계정이 없는 **시험 브로커**(§6) |
| 인바운드 | **8883/TCP** | 0.0.0.0/0 | 4차~ | 운영 브로커 TLS. 인증서 없으면 리스너가 안 뜨므로 미리 열어 둬도 무방 |
| 인바운드 | 80/TCP | 0.0.0.0/0 | 4차 certbot, 3차~ 관리 화면 | HTTP-01 challenge |
| 인바운드 | **443/TCP** | 0.0.0.0/0 | 4차~ | 관리 화면 HTTPS (`docker-compose.tls.yml`). 80 은 리다이렉트 + HTTP-01 로 계속 필요 |
| 아웃바운드 | 전체 | | | |

통신사 NAT 대역은 단말측(모뎀 담당)에게 물어 받는다. 모르면 1차 시험 중에 `docker compose logs mosquitto` 에 찍히는 접속 IP 를 보고 `/24` 로 좁혀 간다. **1883 을 0.0.0.0/0 으로 열어 두고 시험을 시작하지 않는다.**

## 3. 서버 셋업 순서 (최초 1회)

1. AWS 콘솔: EC2 생성(위 표) → EIP 연결 → SG 위 표대로 (1883 은 아직 닫아 두거나 관리자 IP 만).
2. DNS: `infontech.co.kr` A → EIP. `nslookup infontech.co.kr` 로 확인.
3. SSH 접속 후:

```bash
git clone https://github.com/masterjms/solar_power_control.git /tmp/spc && bash /tmp/spc/infra/scripts/setup-ec2.sh
```

   `setup-ec2.sh` 는 멱등이다: apt → Docker + compose 플러그인 → `ubuntu` docker 그룹 → swap 2 GB → ufw 22/1883/8883/80/443 → `/opt/solar_power_control` clone → `.env` 없으면 견본 복사 → `docker compose --profile local-db up -d`. 두 번 돌려도 된다.

4. 로그아웃 → 재접속 (docker 그룹 반영).
5. `.env` 채우기:

```bash
cd /opt/solar_power_control && nano .env      # change-me-db, change-me-mqtt 를 무작위 값으로
```

6. MQTT 계정 등록 (§4 런북 1단계).

## 4. 1차 런북 — 브로커 접속 시험

목표: 사양서 §1.1.8 **1차-A 합격** = 브로커 로그에 24자리 UUID Client ID. B·C 는 같은 세션에서 확인만 한다(실패해도 A 판정을 되돌리지 않는다).

작업 위치는 항상 `/opt/solar_power_control`.

### 4.1 브로커 기동과 계정

```bash
cd /opt/solar_power_control
docker compose up -d mosquitto
docker compose ps                                  # iotlight-mosquitto  running (healthy)
docker compose logs mosquitto --tail 20            # "Opening ipv4 listen socket on port 1883" 와
                                                   # "TLS 인증서 없음 — 8883 리스너를 만들지 않는다 (1차~3차 정상)"
```

공용 시험 계정(사양서 §1.1.2.1)과 서버 계정은 **첫 기동 때 entrypoint 가 자동으로 만든다** — `solarlte-test` 와, compose 가 `.env` 의 `MQTT_PASSWORD` 를 넘기므로 `server` 도. 확인:

```bash
docker compose exec mosquitto sh -c 'cut -d: -f1 /mosquitto/data/passwd'     # solarlte-test, server
```

없거나 비밀번호를 바꿔야 하면(호스트에 mosquitto 설치 없이, 컨테이너 안 `/mosquitto/pw` 사용):

```bash
bash infra/scripts/mosquitto-passwd-add.sh solarlte-test solarlte-test-2026
bash infra/scripts/mosquitto-passwd-add.sh server "$(grep -E '^MQTT_PASSWORD=' .env | cut -d= -f2-)"
```

스크립트는 `/mosquitto/data/passwd` 의 해당 줄을 `user:PBKDF2$sha512$100000$<salt>$<hash>` 형식으로 교체하고 **브로커를 재시작한다**(go-auth 는 HUP 로 못 읽는다 — 접속 중인 단말 전부 재접속). `mosquitto_passwd` 는 쓰지 않는다 — 형식이 달라 go-auth 가 못 읽는다.

### 4.2 브로커 자체 확인 (서버 안에서)

터미널 1:

```bash
bash scripts/mqtt-sub.sh -u solarlte-test -P solarlte-test-2026 -t 'iotlight/#' -v
```

터미널 2:

```bash
bash scripts/mqtt-pub.sh -u solarlte-test -P solarlte-test-2026 -t 'iotlight/server/test' -m 'server-ready' -q 1
```

터미널 1 에 `iotlight/server/test server-ready` 가 보이면 브로커·계정·ACL 이 준비된 것이다.

### 4.3 외부에서 확인 (시험 PC 에서, DNS·SG·ufw 검증)

SG 에 시험 PC 공인 IP 를 1883 으로 열고, PC 에서:

```bash
mosquitto_sub -h infontech.co.kr -p 1883 -u solarlte-test -P solarlte-test-2026 -t 'iotlight/#' -v
```

여기서 막히면 단말은 더 볼 것도 없이 막힌다. 순서대로 확인: `nslookup infontech.co.kr` → EIP 인가 / SG 1883 에 내 IP 있나 / `sudo ufw status` 에 1883 있나 / `docker compose ps` running 인가.

### 4.4 1차-A — 모뎀 접속

서버에서 로그를 연다(systemd 가 아니라 컨테이너라 `journalctl -u mosquitto` 는 없다):

```bash
docker compose logs -f mosquitto
```

SG 에 단말 회선 대역이 열려 있는지 다시 확인한 뒤 단말 전원을 켠다(DIP8 ON, LTE 모드). 다음 세 가지가 모두 보이면 **1차-A 합격**:

1. 단말 로그 `*WMQTCON:2`
2. 단말 로그 `MQTT CONNECTED infontech.co.kr:1883`
3. 브로커 로그에 24자리 대문자 16진수 Client ID 로 새 연결:

```
2026-09-26T10:12:34: New connection from 203.0.113.45:51234 on port 1883.
2026-09-26T10:12:34: New client connected from 203.0.113.45:51234 as 00112233445566778899AABB (p2, c1, k60, u'solarlte-test').
```

`p2` = MQTT 3.1.1, `c1` = clean session, `k60` = keepalive 60 — 사양서 §1.1.2 값과 같아야 한다. 이 시점에 단말이 재접속을 반복하지 않는지(30초마다 New connection 이 찍히면 접속 직후 끊기는 것) 1~2분 지켜본다.

접속한 단말의 공인 IP 를 이 로그에서 읽어 SG 의 1883 규칙을 그 대역으로 좁힌다.

### 4.5 1차-C — Telemetry 확인 (확인만)

```bash
bash scripts/mqtt-sub.sh -u solarlte-test -P solarlte-test-2026 -t 'iotlight/device/+/status' -v
```

REGISTER 직후 1건, 이후 600초마다 1건. `sq` 가 1씩 증가하는지 본다. 한 줄 약 160 바이트, `{"t":"TM",...}` 형태(1차 펌웨어는 `t`, 2차부터 `type`).

### 4.6 1차-B — REGISTER / PING / PONG

**도구를 먼저 켜고 단말을 재부팅한다.** REGISTER 는 (재)연결 때만 온다.

시험 PC 에서 단말측 도구(`Tools/mqtt_test.py`)를 쓰는 것이 원칙이다. 없으면 서버에서 손으로:

터미널 1 (REGISTER 와 PONG 을 본다):

```bash
bash scripts/mqtt-sub.sh -u solarlte-test -P solarlte-test-2026 -t 'iotlight/device/+/register' -t 'iotlight/device/+/result' -v
```

단말 재부팅 → REGISTER 수신 확인(topic 의 UUID 와 payload `uuid` 가 같은지). 터미널 2 에서 PING:

```bash
bash scripts/mqtt-pub.sh -u solarlte-test -P solarlte-test-2026 -t 'iotlight/device/<UUID>/cmd' -q 1 -m '{"type":"PING","seq":1}'
```

터미널 1 에 `iotlight/device/<UUID>/result {"type":"PONG","seq":1,"uuid":"<UUID>"}` 가 오면 통과. **`-r` 은 쓰지 않는다** (cmd 는 절대 retain 하지 않는다).

### 4.7 실패 판단

| 현상 | 우선 확인 |
|---|---|
| PC 에서 TCP 연결 불가 | DNS(`nslookup`), SG 1883 소스 IP, `sudo ufw status`, `docker compose ps` |
| 단말 `*WMQTCON:0` 계속 | 단말 회선 공인 IP 가 SG 에 없다. 통신사 NAT 대역 확인 |
| `MQTT FAIL REASON=3` | 주소·포트·브로커 상태. `docker compose logs mosquitto` 에 접속 시도 자체가 없는지 |
| `MQTT FAIL REASON=4` | 계정. `docker compose exec mosquitto cat /mosquitto/data/passwd` 에 `solarlte-test:` 줄이 있나. 없으면 §4.1 다시. 있으면 기동 뒤에 넣은 것 → `docker compose restart mosquitto`. 단말 UUID 계정이면 backend 가 떠 있나(§10.5) |
| 브로커 로그 `Client ... disconnected due to protocol error` | Client ID 형식이나 MQTT 버전. 단말 로그와 대조 |
| 접속 후 30초마다 재접속 반복 | keepalive/PINGREQ 문제. `k60` 인지, 단말이 PINGREQ 를 보내는지 |
| `*WMQTCON:2` 인데 REGISTER 안 옴 | 1차-A 는 합격. 1차-B topic/payload 단계 — ACL 거부면 브로커 로그에 `Denied PUBLISH` (1차 공용 계정은 전부 허용이라 안 나와야 정상) |
| `Too many open files` | fd 한도. `bash scripts/healthcheck.sh` 의 fd 항목. compose `ulimits` 가 적용 안 된 것 |

- 공용 계정 폐기는 단말 HMAC 펌웨어 전환이 끝난 뒤다(§5.2 전환 순서 5).

## 5. 계정·인증 구조 (ADR-003)

### 5.1 누가 무엇을 판정하나

| 계정 | 판정 주체 | 비밀번호 | ACL |
|---|---|---|---|
| `server` (backend) | go-auth **files** | `.env` `MQTT_PASSWORD` → backend 가 `passwd.generated` 로 내보냄 | `aclfile` `iotlight/#` readwrite |
| `solarlte-test` (1차 공용) | go-auth **files** | `solarlte-test-2026` 고정 (`MQTT_TEST_ACCOUNT_ENABLED=true` 일 때만 포함) | `iotlight/#` readwrite |
| 단말 UUID 24자리 | go-auth **http** → backend `/internal/mqtt/auth`·`/acl` | `HMAC-SHA256(K, UUID)[:16].hex()` — 저장하지 않고 접속마다 계산 | 사양서 §1.1.2.2 표를 코드로(자기 UUID topic 만) |

단말 계정은 passwd 에 없다. `PENDING`/`REJECTED` 도 접속은 된다(사양서 §1.1.2.2 #5) — 승인은 REGISTER 처리에서 가른다.

files 흐름:

1. backend 기동 시 passwd/aclfile 을 임시 파일에 쓰고 원자적으로 교체 → `mqtt-dynamic` 볼륨의 `passwd.generated`, `aclfile.generated`.
2. mosquitto `entrypoint.sh` 감시 루프(1초)가 **내용 md5** 변화를 보고 `mosquitto:mosquitto 0600` 으로 `/mosquitto/data/` 에 설치하고 md5 를 `aclfile.applied`/`passwd.applied` 에 적는다.
3. **aclfile 내용이 바뀌었거나 passwd 의 계정 집합이 바뀌었으면 브로커를 재시작한다**(`kill -TERM 1` → `restart: unless-stopped` 가 되살림). go-auth 가 HUP 로 파일을 다시 읽지 않기 때문이다. 단말 전부 재접속.
4. 계정 집합은 같고 해시만 다르면(backend 는 기동마다 무작위 salt 로 새로 내보낸다) 설치만 하고 재시작하지 않는다 — 그러지 않으면 backend 배포마다 브로커가 재시작된다. **`MQTT_PASSWORD` 를 실제로 바꿨을 때는** `.env` 수정 → `docker compose up -d backend` → `docker compose restart mosquitto`.

운영 확인은 시드가 아니라 설치본을 본다:

```bash
docker compose exec mosquitto sh -c 'cut -d: -f1 /mosquitto/data/passwd; echo ---; cat /mosquitto/data/aclfile'
docker compose exec mosquitto sh -c 'md5sum /mosquitto/dynamic/aclfile.generated; cat /mosquitto/dynamic/aclfile.applied'
```

형식 설명: `infra/mosquitto/config/passwd.seed.md`.

### 5.2 단말 HMAC 전환 순서 (사양서 §1.1.2.2) — 운영자 명령

작업 위치 `/opt/solar_power_control`. `.env.example` 의 `MQTT_HMAC_KEYS` 는 사양서의 **공개 시험 키**(`TEST:0001…1e1f`)다.

**1단계 — 플러그인 설치, 공용 계정 유지.** 이미지가 바뀌므로 pull 이 들어간다(§8 배포 블록과 같다):

```bash
cd /opt/solar_power_control
git pull --ff-only
docker compose pull mosquitto
docker compose build backend
docker compose run --rm --no-deps backend python -m alembic upgrade head
docker compose up -d
docker compose ps
docker compose logs mosquitto --tail 30      # "Backend registered: Files" / "Backend registered: HTTP" / "started go-cache"
bash scripts/mqtt-pub.sh -u solarlte-test -P solarlte-test-2026 -t iotlight/server/test -m still-ok -q 1     # 기존 1.4.0 단말과 같은 계정
```

**2단계 — 시험 키로 확인.** `.env` 의 `MQTT_HMAC_KEYS` 가 `TEST:…` 인 상태에서(사양서 시험값):

```bash
bash scripts/mqtt-pub.sh -u 20363930594D50170004003A -P 70e8a87fba4a997f7c24d1f98300753a -i 20363930594D50170004003A -t iotlight/device/20363930594D50170004003A/status -m '{"type":"TM"}' -q 1      # 성공
bash scripts/mqtt-pub.sh -u 20363930594D50170004003A -P 70e8a87fba4a997f7c24d1f98300753b -i 20363930594D50170004003A -t iotlight/device/20363930594D50170004003A/status -m x -q 1                # "not authorised"
docker compose exec mosquitto tail -5 /mosquitto/dynamic/mosquitto.log     # New client connected ... u'20363930594D50170004003A'
```

**3단계 — 운영 키 `K1` 투입.** 키는 `MQTT_인증키_K1.md` 파일로 별도 전달받는다(메일 본문·사양서·저장소에 없다). 서버 `.env` 에만 넣는다:

```bash
cd /opt/solar_power_control
nano .env      # MQTT_HMAC_KEYS=K1:<파일의 hex 64자>   ← TEST 키는 지운다
docker compose up -d backend
docker compose logs backend --tail 20 | grep -i hmac      # 키 ID 만 찍힌다(값은 절대 로그에 안 남긴다)
bash scripts/mqtt-pub.sh -u <UUID> -P <파일의 확인값> -i <UUID> -t iotlight/device/<UUID>/status -m x -q 1     # 성공
```

키 파일은 확인 뒤 서버에서 지운다. **절대** `git add`, 채팅, 이슈, 로그에 남기지 않는다. 교체 중에는 `MQTT_HMAC_KEYS=K1:<hex>,K2:<hex>` 로 둘 다 허용하고, 단말 펌웨어 교체가 끝나면 `K1` 을 뺀다. go-auth 캐시(600초) 때문에 키를 뺀 뒤 최대 10분은 옛 키로 붙었던 단말이 남아 있을 수 있다.

**4단계 — 단말 HMAC 펌웨어**(단말측). 브로커 로그에 `u'<UUID>'` 로 붙는지 본다:

```bash
docker compose exec mosquitto grep "New client connected" /mosquitto/dynamic/mosquitto.log | tail
```

**5단계 — 공용 계정 삭제.** backend 가 passwd/aclfile 을 다시 내보내고, 계정 집합이 바뀌었으므로 entrypoint 가 브로커를 한 번 재시작한다(단말 전부 재접속 — 시간대 고려):

```bash
cd /opt/solar_power_control
sed -i 's/^MQTT_TEST_ACCOUNT_ENABLED=.*/MQTT_TEST_ACCOUNT_ENABLED=false/' .env
docker compose up -d backend
sleep 10; docker compose ps mosquitto                                        # 재시작 뒤 running (healthy)
docker compose exec mosquitto sh -c 'cut -d: -f1 /mosquitto/data/passwd'    # server 만
bash scripts/mqtt-pub.sh -u solarlte-test -P solarlte-test-2026 -t iotlight/x -m x       # "not authorised"
# 다른 UUID topic 발행 거부 확인(§1.1.8): 서버 계정으로 구독해 두고 단말 계정으로 남의 topic 에 쏘면 아무것도 안 온다
bash scripts/mqtt-sub.sh -u server -P "$(grep -E '^MQTT_PASSWORD=' .env | cut -d= -f2-)" -t 'iotlight/device/00112233445566778899AABB/#' -v -W 10 &
bash scripts/mqtt-pub.sh -u <UUID> -P <그 UUID 의 계산값> -i <UUID> -t iotlight/device/00112233445566778899AABB/status -m INTRUDER -q 1
```

### 5.3 브로커 접속 로그 파일 (ADR-004, Online/Offline)

WD-N522S 는 LWT 를 못 넣으므로 브로커 로그로 접속/해제를 판정한다. `mosquitto.conf` 의 `log_dest file /mosquitto/dynamic/mosquitto.log` 가 `mqtt-dynamic` 볼륨에 쓰고, backend 가 같은 볼륨을 `/var/lib/iotlight/mqtt/mosquitto.log`(`MOSQUITTO_LOG_PATH`) 로 tail 한다. `docker logs`(stderr) 에도 같은 줄이 나간다.

backend 파서가 의존하는 정확한 형식(go-auth 이미지, 2026-09-26 실측 — 타임스탬프 `%Y-%m-%dT%H:%M:%S`, 뒤에 `: `):

```
2026-09-26T09:08:39: New client connected from ::1:38142 as 20363930594D50170004003A (p2, c1, k60, u'20363930594D50170004003A').
2026-09-26T09:13:20: New client connected from ::1:33942 as 20363930594D50170004003A (p2, c1, k60, u'20363930594D50170004003A').
2026-09-26T09:08:39: Client 20363930594D50170004003A disconnected.
2026-09-26T09:13:20: Client 20363930594D50170004003A disconnected.
```

인증 실패는 `Client <id> disconnected, not authorised.` (접속 성공 줄 없이), keepalive 만료는 `Client <id> has exceeded timeout, disconnecting.` 이다. `as <id>` 가 UUID 형식이 아닌 줄(`server`, `healthcheck`, 시험 도구)은 backend 가 무시한다.

권한: 디렉터리 `/mosquitto/dynamic` 은 `10001:mosquitto 2775`(backend 소유, mosquitto 그룹), 로그 파일은 `mosquitto:mosquitto 644` — mosquitto 가 쓰고 backend(uid 10001)가 읽는다. sticky 1777 은 쓰지 않는다(커널 `fs.protected_regular=2` 에서 root 조차 남의 파일을 sticky 디렉터리 안에서 못 열어 truncate 가 실패했다).

회전: entrypoint 감시 루프가 50 MB 를 넘으면 파일을 비우고 mosquitto 에 HUP(재오픈). 백업본은 없다 — 접속 이력의 정본은 DB `device_event` 이고 컨테이너 로그(20 MB×5)가 따로 있다. backend tail 은 크기 감소를 보면 처음부터 다시 읽는다.

## 6. 4차 전환 런북 — MQTTS 8883 + 운영/시험 브로커 분리 (S-21, ADR-006)

전제: 5차 로직이 시험 Broker(1883)에서 먼저 통과했다(사양서 "합격 판정 순서", **2026-09-27 5차 연동 합격**). P-1 조사(모뎀 TLS·루트 CA) 결과 "루트 CA 저장 + 서버 검증 가능"(§1.2.3-2, 2026-09-27 확정). 단말은 루트 **ISRG Root X1** 하나만 펌웨어에 넣고 모뎀 `/data` 에 자동으로 올린다 — 서버 인증서가 90일마다 바뀌어도 단말은 그대로(P-5). 모뎀은 **TLS 1.3 미지원 → 8883 은 TLS 1.2 를 반드시 허용**(`tls_version tlsv1.2` = 1.2 이상, `mosquitto-tls.conf`). 인증서는 **RSA 2048**. 단말 쪽 절차 원본: `docs/spec/tls/TLS_인증서_준비.md`.

### 6.0 무엇이 바뀌나

`docker-compose.tls.yml`(브로커 분리)과 `docker-compose.https.yml`(관리 화면 443, 6.2B — 먼저 켜도 된다)을 `.env` 의 `COMPOSE_FILE` 에 넣으면 켜지고, 빼면 꺼진다. **서버 코드·DB 는 그대로다**(backend 는 계속 컨테이너망 `mosquitto:1883` 평문 — 호스트 밖으로 안 나간다).

| | 전환 전 (1차~3차·5차) | 전환 후 (4차) |
|---|---|---|
| 호스트 1883 | 운영 브로커 `iotlight-mosquitto` (단말 HMAC·server·solarlte-test) | **시험 브로커 `iotlight-mosquitto-test`** (`eclipse-mosquitto:2`, 계정 `solarlte-test` 하나뿐, backend 안 붙음) |
| 호스트 8883 | (인증서 없으면 리스너 없음) | 운영 브로커 TLS 1.2+ — 단말 HMAC 계정, server |
| 운영 브로커 1883 | 호스트 공개 | 컨테이너망 안 backend 전용(비공개) |
| 관리 화면 | `http://` 80 | `https://` 443, 80 은 301 리다이렉트(`/.well-known/acme-challenge/` 와 Host `localhost` 만 예외) |

합격 기준 §1.2.4 #1 "1883 은 운영 계정 거부" = 호스트 1883 의 시험 브로커에 운영 계정이 **아예 없다**(구조로 성립). 인증서: `certbot` 컨테이너(`--webroot`, web nginx 경유) → `infra/letsencrypt/` → `infra/certs/server.crt|key` 복사 → mosquitto·nginx 가 읽는다.

**mosquitto 2.0.15 는 리스너 인증서를 실행 중에 다시 읽지 않는다.** 새 인증서 = 브로커 재시작 = 단말 전부 재접속. 그래서 갱신 적용은 새벽 03:30 KST 한 번만, 인증서가 실제로 바뀐 날에만 한다(약 60일에 1번, §6.6). 키 파일은 **root:1000 0640** 이어야 한다 — mosquitto 가 권한을 내려놓은 뒤(uid 1000) 키를 읽는다(0600 root 면 `Unable to load server key file ... Permission denied` 로 기동 실패, 2026-09-27 실측). 스크립트가 맞춰 준다.

### 6.1 (사전) DNS·SG 확인

```bash
dig +short infontech.co.kr          # EIP 가 나와야 한다
```

AWS SG 인바운드에 **8883/TCP 0.0.0.0/0**, **443/TCP 0.0.0.0/0**, 80/TCP 0.0.0.0/0 (HTTP-01·리다이렉트) 가 있어야 한다(§2.1). ufw 는 `setup-ec2.sh` 가 이미 22/1883/8883/80/443 을 연다(`sudo ufw status` 로 확인). 1883 은 전환 뒤에도 **시험 접속원 IP 제한 그대로** 둔다(시험 브로커).

### 6.2 인증서 발급 (서비스 중단 없음 — 켜기 전 언제든)

```bash
cd /opt/solar_power_control && git pull --ff-only
docker compose up -d web                                             # certbot-www 볼륨을 물린 web
STAGING=1 bash infra/scripts/cert-issue.sh infontech.co.kr <운영자 이메일>   # 연습(스테이징, 한도 소모 없음). 선택
bash infra/scripts/cert-issue.sh infontech.co.kr <운영자 이메일>
openssl x509 -in infra/certs/server.crt -noout -subject -issuer -dates
ls -ln infra/certs/                                                   # server.crt 644 0:0, server.key 640 0:1000
```

스테이징 연습을 했다면 본 발급 전에 `docker compose run --rm certbot delete --cert-name infontech.co.kr` 로 지운다(스테이징 인증서가 남아 있으면 `--keep-until-expiring` 이 재발급을 건너뛴다).

**키는 RSA 2048** 이다(2026-09-28 단말 담당 요구, 문제점 #9 — 모뎀의 ECDSA 지원 미확인). `cert-issue.sh` 가 `--key-type rsa --rsa-key-size 2048` 로 받고, 끝에 `Public Key Algorithm: rsaEncryption` 인지 확인해 아니면 멈춘다. 확인은 `openssl x509 -in infra/certs/server.crt -noout -text | grep 'Public Key Algorithm'`.

### 6.2A 8883 먼저 열기 — 1883 은 그대로 (단말 MQTTS 시험용, 2026-09-28)

단말 담당 순서: **서버가 8883(TLS 1.2 허용)을 열고 `openssl s_client` 결과(`Verify return code: 0 (ok)`)를 알려 주면** 단말이 MQTTS 를 켜고 시험한다. 그동안 1883 의 기존 단말이 끊기면 안 되므로, 6.3 의 브로커 분리 전에 **운영 브로커만 다시 만들어** 8883 을 연다(entrypoint 가 인증서를 보고 TLS 리스너를 붙인다, 1883 은 그대로 운영 계정 허용). 단말은 재접속 1회(30초 안).

```bash
cd /opt/solar_power_control
docker compose up -d --force-recreate mosquitto
docker compose logs mosquitto --tail 30 | grep -E 'TLS 리스너|8883'        # "TLS 리스너 8883 활성"
openssl s_client -connect infontech.co.kr:8883 -servername infontech.co.kr -tls1_2 -showcerts </dev/null 2>/dev/null \
  | grep -E 'Verify return code|Protocol|Cipher is|^ *[0-9] s:|^ *i:'
```

기대: `Protocol : TLSv1.2`, 사슬 `0 s:CN = infontech.co.kr` → `1 s:… CN = R1x`(Let's Encrypt 중간) → `i:… CN = ISRG Root X1`, **`Verify return code: 0 (ok)`**. 이 출력을 그대로 단말 담당에게 보낸다. 단말이 8883 합격하면 6.3 으로 브로커를 나눈다(운영 계정은 8883 에만).

### 6.2B 관리 화면 HTTPS 켜기 — 브로커와 따로 (2026-09-28)

6.2A 는 **MQTT 8883 만** 연다. 관리 화면(443)은 원래 6.3 브로커 분리(`docker-compose.tls.yml`)에 묶여 있어서, 8883 을 열어도 사이트는 `http://` 그대로였다(실제로 겪음).
이제 web 부분만 `docker-compose.https.yml` 로 떼었다 — **web 만 다시 만들고 브로커·단말은 건드리지 않는다.** SG 에 443/TCP 가 열려 있어야 한다.

```bash
cd /opt/solar_power_control
echo 'COMPOSE_FILE=docker-compose.yml:docker-compose.https.yml' >> .env
docker compose up -d --no-deps web
docker compose logs web | grep 모드                                              # "TLS 모드: 443 활성, 80 → https 리다이렉트"
curl -s -o /dev/null -w '%{http_code} %{redirect_url}
' http://infontech.co.kr/   # 301 https://infontech.co.kr/
curl -s -o /dev/null -w '%{http_code}
' https://infontech.co.kr/                  # 401 (Basic auth)
```

카카오 콘솔 [플랫폼 > Web > 사이트 도메인]에 `https://infontech.co.kr` 을 추가한다(지도). 끄기: `.env` 의 그 줄을 지우고 `docker compose up -d --no-deps web`.

`cert-issue.sh` 는 먼저 `http://<도메인>/.well-known/acme-challenge/<토큰>` 이 이 서버 web 으로 오는지 확인하고, 안 오면 발급을 시도하지 않고 멈춘다(DNS·SG 문제). 인증서만 만들고 **컨테이너는 건드리지 않는다.**

### 6.3 전환 (단말 전부 재접속 1회 — 시험 단말만 있을 때, 새벽 권장)

```bash
cd /opt/solar_power_control
sed -i '/^COMPOSE_FILE=/d' .env     # 6.2B 의 https 줄을 바꾼다
echo 'COMPOSE_FILE=docker-compose.yml:docker-compose.https.yml:docker-compose.tls.yml' >> .env
# 선택: 시험 브로커 solarlte-test 비밀번호를 공개값(solarlte-test-2026) 대신 쓰려면
# echo 'MQTT_TEST_BROKER_PASSWORD=<값>' >> .env
```

#3 의 가짜 브로커(서버에서, 30초면 된다 — 끝나면 지운다):

```bash
mkdir -p /tmp/fake && cd /tmp/fake && openssl req -x509 -newkey rsa:2048 -nodes -keyout k.pem -out c.pem -days 1 -subj /CN=infontech.co.kr
printf 'listener 18883\nallow_anonymous true\ncertfile /f/c.pem\nkeyfile /f/k.pem\n' > m.conf && chmod 644 k.pem

# SG 에 18883 을 시험 IP 로 잠깐 열고, 단말 포트를 18883 으로 바꾼 F/W 로 접속 → 단말 거부 확인. 끝나면 SG 규칙·/tmp/fake 삭제
```

로컬 사전 측정(2026-09-27, Windows Docker, 자체 CA 2단 체인 RSA-2048 — LE 의 leaf+R1x 와 같은 구성, TLS 1.2 `ECDHE-RSA-AES256-GCM-SHA384`, 세션 재개 없음): **TLS 핸드셰이크 2,566 B**(송 273 / 수 2,293) + CONNECT·CONNACK·DISCONNECT 포함 **재접속 1회 2,757 B** (TCP/IP 헤더 제외 — 세그먼트 약 7개 + TCP 3-way/ACK/FIN 까지 더하면 대략 +0.5 KB, **약 3.2~3.3 KB**). 평문 1883 은 같은 조건 104 B(+TCP 약 0.4 KB). 즉 TLS 로 재접속 1회당 약 2.7 KB 가 는다. 서버 인증서 체인이 대부분(수신 2.3 KB)이라 LE 가 ECDSA 체인(E5/E6)을 주면 줄어든다. 실측(모뎀 카운터)으로 확정한다.

### 6.6 자동 갱신 cron

`cert-renew.sh` = `certbot renew`(만료 30일 전부터만 실제 갱신) → `live/<도메인>/fullchain.pem` 과 `infra/certs/server.crt` 의 sha256 비교 → 다르면 복사(권한 포함) + `docker compose restart mosquitto` + `nginx -s reload`. 같으면 아무것도 안 한다. `--renew-only` 는 갱신만 하고 설치하지 않는다 — 낮에 갱신돼도 적용(=브로커 재시작)은 그날 03:30 에 된다.

EC2 의 시간대를 먼저 본다(`timedatectl | grep 'Time zone'`, Ubuntu 기본 UTC). **UTC 서버 기준** (03:30 KST = 18:30 UTC, 15:30 KST = 06:30 UTC):

```bash
( crontab -l 2>/dev/null; \
  echo '30 18 * * * cd /opt/solar_power_control && bash infra/scripts/cert-renew.sh >> $HOME/cert-renew.log 2>&1'; \
  echo '30 6 * * * cd /opt/solar_power_control && bash infra/scripts/cert-renew.sh --renew-only >> $HOME/cert-renew.log 2>&1' ) | crontab -
crontab -l
bash infra/scripts/cert-renew.sh            # 수동 1회 — "인증서 변화 없음 — 재시작 안 함"
docker compose run --rm certbot renew --dry-run --webroot -w /var/www/certbot     # 갱신 경로 연습
```

(서버가 Asia/Seoul 이면 `30 3` / `30 15`.) 스크립트는 `logger -t iotlight-cert` 로 syslog 에도 남긴다(`journalctl -t iotlight-cert`). `healthcheck.sh` 가 만료 20일 전부터 FAIL 을 낸다. 리프만 바뀌고 루트(ISRG Root X1)는 그대로라 모뎀 루트 CA 는 손대지 않는다(P-5).

## 6A. 관리 화면 (nginx + Basic auth) — 3차~

- 접속: `http://infontech.co.kr/` (또는 `http://<EIP>/`). 브라우저가 계정을 물으면 서버 `.env` 의 `ADMIN_USER` / `ADMIN_PASSWORD`.
- 구성: `web` 컨테이너(`iotlight-web`, `frontend/Dockerfile`) = Vite 빌드 결과를 nginx 가 서빙 + `/api/`, `/health` 를 `backend:8000` 으로 프록시. `/internal/` 은 404 로 명시 차단. backend 8000 은 여전히 호스트에 열지 않는다 — 밖에서 백엔드에 닿는 길은 이 nginx 하나다.
- **왜 Basic auth 인가**: `/api` 에 아직 로그인이 없다(docs/05). 로그인 기능이 붙을 때까지 nginx 가 전 경로(정적 파일 포함)에 HTTP Basic auth 를 거는 임시 보호다. 계정은 컨테이너 기동 시 `frontend/nginx/30-htpasswd.sh` 가 `.env` 값으로 `/etc/nginx/.htpasswd` 를 만든다. `ADMIN_PASSWORD` 가 비었거나 견본 값 `change-me-admin` 이면 컨테이너가 **기동을 거부**한다.
- **계정 2개 (5차, ADR-005)**: `ADMIN_USER`/`ADMIN_PASSWORD`(필수) + 선택 `OPERATOR_USER`/`OPERATOR_PASSWORD`(둘 다 채웠을 때만 추가, 한쪽만 채우면 기동 거부). 로그 `htpasswd 생성: 사용자 admin op1`.
- **사용자명 전달**: nginx 가 인증된 사용자명(`$remote_user`)을 `X-Remote-User` 헤더로 `/api/`·`/health` 에 실어 보낸다(`frontend/nginx/routes.conf`). 클라이언트가 같은 헤더를 보내도 **nginx 값으로 교체**된다 — 위조 헤더 2개(`X-Remote-User: evil`, `x-remote-user: evil2`)를 보내도 backend 에는 `X-Remote-User: op1` 한 줄만 도착(2026-09-27 에코 서버로 실측). backend 가 `.env SUPER_ADMIN_USERS`(기본 `admin`)로 최고관리자(전체 명령·트리 편집)를 판정한다. backend 8000 은 호스트에 열지 않으므로 이 헤더를 신뢰할 수 있다 — **운영 compose 에 backend 포트를 열면 이 전제가 깨진다.**
- Security Group: 80/TCP 가 0.0.0.0/0 으로 열려 있어야 한다(§2.1 — 이미 열려 있음). ufw 도 `setup-ec2.sh` 가 80 을 열어 둔다.
- **HTTPS 는 4차 오버라이드와 함께**(§6): `docker-compose.tls.yml` 이 `./infra/certs` 를 `/etc/nginx/certs` 로 물리면 `40-tls.sh` 가 기동 때 443 server 를 만들고 80 을 301 리다이렉트로 바꾼다(예외: `/.well-known/acme-challenge/`, Host `localhost`/`127.0.0.1` — 컨테이너·호스트 점검용). 그때까지 Basic auth 는 평문으로 오간다 — 비밀번호를 다른 곳과 공유하지 말 것. `/.well-known/acme-challenge/` 는 평문 모드에서도 항상 무인증으로 열려 있다(certbot `--webroot`, 토큰 파일만 있는 `certbot-www` 볼륨).
- 계정 바꾸기: `.env` 수정 → `docker compose up -d web` (컨테이너 재생성 때 htpasswd 가 다시 만들어진다).
- 로컬(Windows): `docker-compose.dev.yml` 이 `!override` 로 호스트 포트를 `8088` 로 바꾼다 → `http://localhost:8088/`.
- 점검: `scripts/healthcheck.sh` 가 `.env` 의 ADMIN_* 로 `http://localhost/health` 가 200, 무인증이면 401 인지 본다. 4차 모드면 `https://localhost/health` 200 도 본다.
- 설정 확인: `docker compose exec web nginx -T | grep -n 'X-Remote-User\|listen'`.

## 8. 배포 절차 (담당자용, 한 블록)

```bash
cd /opt/solar_power_control && bash scripts/deploy.sh
```

`deploy.sh` 가 하는 일: `.env` 확인 → `git pull --ff-only` → `docker compose pull mosquitto` → `docker compose build backend web` → **컨테이너 교체 전에** `alembic upgrade head` → `docker compose up -d` → `scripts/healthcheck.sh`. 마이그레이션이 실패하면 기존 컨테이너를 건드리지 않고 멈춘다.

**이번 배포(관리 화면 `web` 추가) 전에 `.env` 에 두 줄을 추가해야 한다.** 서버의 `.env` 는 옛 견본으로 만들어져 이 키가 없고, 없으면 `web` 컨테이너가 기동을 거부한다:

```bash
cd /opt/solar_power_control
cat >> .env <<'EOF'
ADMIN_USER=admin
ADMIN_PASSWORD=<무작위 비밀번호>
EOF
# change-me-admin 이거나 비어 있으면 web 이 안 뜬다
```

**5차 배포(법정동 트리·COMMAND·권한, ADR-005) 전에 `.env` 에 추가할 줄** — 없는 키만 넣는다(`grep -E '^(OPERATOR_|SUPER_ADMIN_USERS|KAKAO_REST_API_KEY|APPROVE_REQUIRES_NODE|COMMAND_)' .env` 로 먼저 확인):

```bash
cd /opt/solar_power_control
cat >> .env <<'EOF'
# 5차 (ADR-005)
OPERATOR_USER=
OPERATOR_PASSWORD=
SUPER_ADMIN_USERS=admin
KAKAO_REST_API_KEY=<카카오 로컬 REST 키>
APPROVE_REQUIRES_NODE=true
COMMAND_EXP_SEC=30
COMMAND_TIMEOUT_SEC=900
COMMAND_MAX_ATTEMPTS=3
COMMAND_RETRY_MIN_SEC=20
EOF
bash scripts/deploy.sh                       # backend·web 재빌드 + 마이그레이션 + 교체
docker compose exec web nginx -T | grep -c 'X-Remote-User $remote_user'   # 2
```

`OPERATOR_*` 는 두 번째 계정(최고관리자 아님)이 필요할 때만 채운다. `APPROVE_REQUIRES_NODE=true` 면 법정동 말단을 배정해야 승인된다 — 트리에 법정동을 먼저 만든다. 이번 배포는 mosquitto conf 가 안 바뀌어 브로커 재생성·단말 재접속이 없다.

옵션: `--no-pull`(현재 체크아웃 그대로), `--infra-only`(mosquitto/postgres 만 — 1차, 또는 conf 만 바꿨을 때. `backend/Dockerfile` 이 없으면 자동).

손으로 풀어 쓰면(이번 배포는 브로커 이미지가 `iegomez/mosquitto-go-auth` 로 바뀌므로 `docker compose pull mosquitto` 가 들어간다 — mosquitto 컨테이너가 재생성되어 단말 전부 재접속):

```bash
cd /opt/solar_power_control
git pull --ff-only
docker compose pull mosquitto
docker compose build backend web
docker compose run --rm --no-deps backend python -m alembic upgrade head
docker compose up -d
docker compose ps
docker compose logs mosquitto --tail 30     # "Backend registered: Files" / "Backend registered: HTTP"
docker compose logs web --tail 10           # "htpasswd 생성: 사용자 admin"
docker compose exec mosquitto sh -c 'cut -d: -f1 /mosquitto/data/passwd; ls -la /mosquitto/dynamic/mosquitto.log'
bash scripts/healthcheck.sh
curl -s -o /dev/null -w '%{http_code}
' http://localhost/            # 401
curl -s -u admin:<비밀번호> http://localhost/health                     # backend JSON
```

옛 `eclipse-mosquitto` 시절 `mosquitto-data` 볼륨에 남은 `/mosquitto/data/passwd`(`$7$…` 형식)는 go-auth 가 못 읽는다. backend 가 뜨면 `passwd.generated` 로 덮어 설치되지만(계정 집합이 같으면 재시작 없이 설치만 되어 옛 파일이 메모리에 남는다), `server` 접속이 계속 거부되면 `docker compose exec mosquitto rm /mosquitto/data/passwd && docker compose restart mosquitto` 로 시드부터 다시 만들게 한다.

되돌리기: `git checkout <이전 SHA> && bash scripts/deploy.sh --no-pull` (스크립트가 실패 시 SHA 를 알려준다). 새 마이그레이션이 옛 코드와 안 맞으면 downgrade 를 먼저 검토한다.

mosquitto 컨테이너가 재생성되는 배포(conf·entrypoint 변경)는 단말 전체 재접속을 일으킨다. 단말 backoff 지터 확인 전엔 시험 단말만 있을 때 한다.

## 9. 백업

DB 는 `pg_dump` 를 매일 03:10 KST 에 뜬다(local-db 프로파일 기준. RDS 전환 후엔 RDS 자동 백업 + PITR 로 대체).

```bash
mkdir -p ~/db-backups
( crontab -l 2>/dev/null; echo '10 3 * * * cd /opt/solar_power_control && docker compose exec -T postgres pg_dump -U iotlight --clean --if-exists iotlight | gzip > ~/db-backups/iotlight-$(date +\%F).sql.gz && find ~/db-backups -name "iotlight-*.sql.gz" -mtime +7 -delete' ) | crontab -
( crontab -l 2>/dev/null; echo '30 8 * * * cd /opt/solar_power_control && bash scripts/healthcheck.sh --slack >/dev/null 2>&1' ) | crontab -
crontab -l
```

`healthcheck.sh` 가 30시간 넘게 새 백업이 없으면 경고한다. 복구:

```bash
docker compose stop backend
zcat ~/db-backups/iotlight-<날짜>.sql.gz | docker compose exec -T postgres psql -U iotlight iotlight
docker compose start backend
```

telemetry 가 커지면(수 GB) 덤프 대신 EBS 스냅샷 + RDS 전환을 앞당긴다. `mosquitto-data` 볼륨(retained REGISTER_ACK)은 DB 에서 재발행 가능하므로 백업하지 않는다(CLAUDE.md "DB 가 정본, retain 은 캐시").

## 10. 장애 시 확인 순서

### 10.1 단말 다수가 동시에 오프라인

1. `bash scripts/healthcheck.sh` — 컨테이너, 1883/8883 리스너, fd, 디스크
2. `docker compose logs --tail 200 mosquitto` — `Too many open files`, `Socket error`, 인증 실패(`Client ... disconnected, not authorised`) 급증 여부. 인증 실패가 전 단말이면 §10.5(backend 다운 또는 키)
3. 4차 이후: 인증서 만료(`healthcheck.sh` 항목) / `openssl s_client -connect infontech.co.kr:8883`
4. `aclfile.generated` ≠ `aclfile.applied` 면 entrypoint 감시 루프가 멈춘 것 → `docker compose restart mosquitto`
5. backend 의 서버 계정 연결: `/health` 의 mqtt 항목
6. 브로커가 복구된 뒤 단말이 지터를 두고 재접속하는지 로그의 New connection 분포로 확인. 30초 간격으로 1만 건이 한꺼번에 오면 단말측에 지터 요청(개발계획 §7)

### 10.2 Telemetry 는 오는데 DB 에 안 쌓임

1. `/health` 의 database 항목, backend 로그의 `telemetry_dropped` 카운터
2. `docker compose exec postgres pg_isready`, 디스크 여유
3. 이번 달·다음 달 파티션 존재: `\d+ telemetry` — 없으면 backend 가 기동 시 만든다 → `docker compose restart backend`

### 10.3 CONFIG_SET 을 보냈는데 CONFIG_ACK 가 없음

1. 단말이 `config` topic 을 구독하는 펌웨어인가(1차 펌웨어는 안 한다)
2. `aclfile.applied` 가 최신인가 (§5 "ACL 먼저")
3. `bash scripts/mqtt-sub.sh -t 'iotlight/device/<uuid>/#' -v` 로 실제 발행이 나가는지
4. 단말 `cv` 가 이미 같으면 backend 는 안 보낸다 — `device.cv_server` vs `cv_device`

### 10.4 디스크 가득

1. `docker system df`, `du -sh /var/lib/docker/volumes/*` — 보통 pgdata(telemetry) 아니면 컨테이너 로그
2. 로그: compose `x-logging` 이 적용됐는지 `docker inspect iotlight-mosquitto | grep -A3 LogConfig`
3. telemetry: 오래된 파티션 DROP 이 돌았는지(`TELEMETRY_RETENTION_MONTHS`)
4. `docker image prune -f`

### 10.5 backend 가 죽으면 단말 신규 접속 불가 (ADR-003 결과)

단말 인증은 go-auth → backend HTTP 다. backend 가 내려가 있으면 **캐시(600초+지터)에 없는 단말의 접속은 거부**되고(`not authorised`, 단말은 `MQTT FAIL REASON=4` 로 본다), 캐시된 단말은 TTL 동안 붙는다. 이미 붙어 있는 세션은 끊기지 않는다(ACL 은 캐시로 판정, 캐시 만료 뒤 발행은 거부될 수 있다). `server`/`solarlte-test` 는 files 라 영향 없다.

1. `docker compose ps backend`, `docker compose logs --tail 100 backend` — `restart: unless-stopped` 라 보통 스스로 올라온다
2. `docker compose exec backend python -c "import urllib.request;print(urllib.request.urlopen('http://localhost:8000/health').status)"`
3. 복구되면 단말은 재접속 간격대로 다시 붙는다. 브로커 로그에 `New client connected ... u'<UUID>'` 가 다시 늘어나는지
4. 전 단말이 계속 `not authorised` 면 키: `.env` `MQTT_HMAC_KEYS` 의 키 ID 가 단말 펌웨어 키와 맞나(값은 로그에 없다 — 사양서 시험값으로 §5.2 2단계를 다시 해 본다)

### 10.6 서버 자체가 안 뜸

CloudWatch StatusCheckFailed. EC2 재부팅 → `restart: unless-stopped` 로 컨테이너가 스스로 올라온다. swap 이 fstab 에 있는지(`swapon --show`), `docker compose ps` 로 3개 running 확인.
