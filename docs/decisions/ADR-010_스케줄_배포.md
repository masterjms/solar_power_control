# ADR-010 스케줄 배포(S-25) — 프로필 · 트리 배정 · 단말마다 SETTINGS_SET(tbl)

- 날짜: 2026-09-29
- 상태: 확정 (사양서 §13.1 [추천], UI 명세 8.4, `서버_업무_2026-09-29.md` W-2)

## 결정

### 메시지는 새로 만들지 않는다 [필수]
- S-23 `SETTINGS_SET` 에 `tbl`(`region lat_e6 lon_e6 on off crc`)을 실어 **단말마다** `device/{uuid}/cmd` 로 보낸다.
  `SCHEDULE_UPDATE`·chunk 전송은 쓰지 않는다(단말에 없음). `crc` = `suntable.table_crc32(build_table(...))` 그대로
  (vendored `suntable.py`, 서울 `69C1DF86` 단위 시험 고정). 단말이 같은 식으로 계산해 같을 때만 저장하고 `OK`.
- 요청 수명(30초 무응답 → 새 seq, 3회 → TIMEOUT, 단말이 보낸 직후 바로 재발송)은 S-23 `settings_sync` 그대로.

### 프로필 = 조건 + 운전 15개
- `schedule_profile`: 이름·**version**·`region`(앞뒤 공백·BOM 제거, UTF-8 47B)·`lat_e6 lon_e6`·`on off`(−180~180)·`crc`·`values`(15개).
- 15개 = `ui_items.json` 그룹 `schedule`(시작/종료 Offset·시작 밝기) + `stage`(다단계 1~4 시·분·밝기). 키를 코드에 적지 않고 스키마에서 뽑는다.
- **넣지 않는 10개**(기준 밝기 PWM1~3·fade·배터리 6)는 단말마다 다르다 — 배포 때 **그 단말의 마지막 읽은 값**을 그대로 보낸다.
- 조건이나 15개가 바뀌면 version +1. 이미 적용된 단말은 "옛 판"이 되어 다시 배포할 대상이 된다.

### 배정 = 트리 상속 + 단말 예외
- `schedule_assign`: 노드 하나 또는 단말 하나 → 프로필(CHECK 로 둘 중 하나).
- 단말의 프로필 = 단말 배정 → 없으면 **말단부터 위로 가장 가까운 노드 배정**. 배정은 저장만, 배포는 따로 누른다.

### 배포 = 작업 + 단말별 항목, 러너가 끌고 간다
- `deploy_job`(프로필 한 판 — `spec` 에 조건·15개를 복사해 두어 배포 중 프로필이 바뀌어도 그 판으로 끝낸다) +
  `deploy_item`(단말별 `waiting → reading → sent → 결과`).
- 범위: 프로필 전체 / 노드 아래 / 단말 하나. 대상 = 범위 안 **ACTIVE** 이면서 **지금 배정이 그 프로필**인 단말. 없으면 409 `DEPLOY_NO_TARGETS`.
- 같은 단말의 진행 중 항목은 새 작업이 `SUPERSEDED` 로 대체한다.
- `mqtt/deploy_runner.py`(5초 틱 + 단말이 보낸 직후):
  - 오프라인이거나 다른 설정 요청이 진행 중이면 **대기** — 다시 접속(REGISTER·Telemetry)하면 자동(§13.1 추천).
  - 서버가 단말 값을 모르거나(`unknown`) 현장에서 바뀌었을 수 있으면(`local_saved`·`device_changed`) **`SETTINGS_GET` 먼저**
    (현장 기준 밝기·배터리 값을 덮지 않으려는 것 — "읽고 나서 쓴다", ADR-007).
  - 25개 = 마지막 읽은 값 + 프로필 15개 → 서버 검사(범위·규칙 — 단말 쪽 배터리 값이 규칙을 어기면 `RULE` 로 끝, 보내지 않음).
  - 초당 10대 이하(`DEPLOY_RATE_PER_SEC`, 틱 5초 × 10 = 50).
  - 결과: `OK`(= 적용됨, `device_schedule` 기록) / `CRC RULE RANGE BAD STATE FLASH` / 3회 무응답 `NO_RESPONSE` / 읽기 실패 `READ_FAILED`.
  - 이 항목이 낸 요청은 `command.created_by = "deploy#<job>"` 로 알아본다(재발송은 새 seq — 가장 최근 행의 결과).
- "응답 없는 단말만 다시": 실패 항목을 `waiting` 으로, 항목당 `DEPLOY_MAX_ROUNDS`(3) 번까지. 취소: 열린 항목 `CANCELLED`
  (이미 보낸 요청은 단말이 적용할 수 있다 — 결과는 무시).

### 적용 확인 · 감시
- `device_schedule`(단말별 적용 판·crc·15개). "적용됨" = 적용 판이 **지금 배정 프로필의 현재 판**이고, 단말이 마지막으로 알려 준 표 crc 가 같음.
- 알람 "스케줄 불일치"(ADR-009): 적용 crc ≠ 단말이 마지막으로 알려 준 표 crc. 현장 저장(`ss` 변화) → 다시 읽기에서 드러난다.
  서버는 자동으로 덮어쓰지 않는다(관리자가 다시 배포).

### API
`/api/schedule/profile-keys · profiles(CRUD) · assign(GET/PUT) · devices · deploy(POST/GET) · deploy/{id}(GET) · /retry · /cancel`,
`/api/devices/{uuid}/schedule`(단말 상세 스케줄 탭). docs/05 "스케줄 배포 API".

## 결과
- 원격 명령(문제점 14번)은 "오프라인이면 안 보냄"인데 배포는 "오프라인이면 대기했다가 자동" — 명령은 지금의 조작이고, 배포는 결국 맞춰야 하는 상태라서 다르게 둔다.
- 1만 대 배포는 초당 10대면 약 17분 + 오프라인 대기. 속도는 `.env` 로 조정.
