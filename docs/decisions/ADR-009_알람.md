# ADR-009 알람(조치 필요) — S-24

- 날짜: 2026-09-29
- 상태: 확정 (사양서 §16.6, `서버_업무_2026-09-29.md` W-1. 16.6.1 은 단말 확정, 16.6.2~3 은 [추천])

## 결정

### 판정은 "주기 재조정" 하나로
- 30초마다(`ALARM_EVAL_SEC`) **지금 DB 상태로 "열려 있어야 할 알람" 집합을 SQL 로 만들고**, 열린 알람과 맞춘다.
  새로 생긴 것 = 열기, 계속 = `last_seen_at` 갱신, 없어진 것 = 닫기(이력). 이벤트마다 열고 닫는 방식보다 단순하고,
  서버 재시작·놓친 메시지에도 스스로 맞춰진다(멱등). 1만 대 × 항목 12개도 쿼리 몇 개다.
- 지연은 최대 30초. 단말이 `er` 변화를 2초 뒤 Telemetry 로 앞당겨 보내므로(§16.6.1) 화면 반영은 1분 안.
- 과보고 방지는 단말이 한다(10분 5건). 서버는 Telemetry 의 `er` 를 현재 값으로 믿는다.

### 테이블 `alarm` (DB 0007)
`id, uuid, kind, severity, first_seen_at, opened_at, last_seen_at, closed_at, value jsonb`
- **한 단말·한 항목 열린 알람 1건** = 부분 유니크 인덱스 `(uuid, kind) WHERE closed_at IS NULL`.
- 지속 조건이 있는 항목(설정 불일치 30분, 현장 조작 1시간)은 조건이 처음 보인 때 `first_seen_at` 만 적은 **관찰(watch)** 행으로
  두었다가(`opened_at` NULL, 화면에 안 보임) 시간이 차면 연다. 그 전에 조건이 사라지면 관찰 행은 지운다(이력 아님).
- 해제 = `closed_at`. 다시 생기면 새 행(새 건). 이력 보존 365일(device_event 와 같이 일 배치 삭제).

◆ 통신 두절: 추천안은 `ti × 2 + 5분`. 우리 화면의 온라인 판정(목록·지도·명령 대상)은 이미 "브로커 연결 AND `ti × 3` 안에 수신"이라,
알람만 다른 기준을 쓰면 "목록은 온라인인데 알람은 두절"이 생긴다. **한 기준**으로 맞춘다. 기본 `ti` 600초면 30분.

- 대상: **ACTIVE 만**(승인 대기 항목은 PENDING). SUSPENDED 는 통신 두절을 만들지 않는다. REJECTED·RETIRED 는 알람 없음 —
  상태가 바뀌면 그 단말의 열린 알람은 다음 재조정에서 닫힌다.
- `er` 0x0008(예약)·0x0040(LTE_OFFLINE) 은 알람이 아니다.
- 오프라인 단말의 `er` 고장 알람은 마지막으로 받은 값으로 유지한다(모르면 닫지 않는다).
- 정렬: 등급(경고 → 주의 → 정보) → 발생 최신순. 목록 열: 등급 · 항목 · 단말(시설명·주소·UUID) · 발생 · 지속 · 마지막 값.

### API
`GET /api/alarms?status=open|closed&tab=&q=&page=&size=` (+ 탭별 건수), `GET /api/devices/{uuid}/alarms`.
대시보드 "조치 필요" 카드는 이 API 로 바꾼다(전에는 화면이 목록에서 계산).

## 결과
- 알림(문자·메일)은 뒤 단계 — `alarm` 행이 생길 때가 붙일 자리다.
- 기준 시간은 전부 `.env` 로 바꿀 수 있다(운영하며 조정).
