# ADR-011 관리 화면 로그인 — Basic auth 창 대신 로그인 화면 + 세션 쿠키

- 날짜: 2026-09-30
- 상태: 확정 (문제점 16번)

## 배경
관리 화면은 3차부터 nginx HTTP Basic auth 로 전 경로를 막아 왔다(로그인 기능이 붙을 때까지의 임시 장치, docs/04 §6A).
스마트폰에서 `https://infontech.co.kr/` 을 열면 `401 Authorization Required` 만 보였다 — 메신저 앱 안의 브라우저
(카카오톡 등)는 Basic auth 입력 창을 띄우지 않는다. 창을 띄우는 브라우저도 계정 저장·로그아웃이 안 된다.
또 폭이 고정된 사이드바(216px) 때문에 폰에서는 화면이 약 1,060px 로 그려져 작게 축소됐다.

## 결정
- **로그인 판정은 backend 가 한다**(`core/web_session.py`, `/api/auth/*`). 계정은 그대로 `.env` 의
  `ADMIN_USER/ADMIN_PASSWORD`(+ 선택 `OPERATOR_*`) — backend 는 `env_file: .env` 로 이미 받는다.
- **nginx 는 `auth_request`** 로 `/api/*`·`/health` 앞에서 `GET /api/auth/check` 를 묻고, 돌려받은 `X-Auth-User` 를
  지금처럼 `X-Remote-User` 로 넘긴다. ADR-005 권한(SUPER_ADMIN_USERS)·명령 이력의 "누가"는 바뀌지 않는다.
- 판정 = **세션 쿠키** `iotl_session`(사용자.만료.HMAC-SHA256, HttpOnly, SameSite=Lax, https 면 Secure, 기본 7일
  `SESSION_HOURS`) → 없으면 **`Authorization: Basic`**(scripts/healthcheck.sh 등 스크립트용).
- 서명 키 `SESSION_SECRET`, 비우면 계정 비밀번호에서 유도 → 비밀번호를 바꾸면 모든 세션이 끊긴다. 쿠키의 사용자가
  지금 계정에 없으면 거부.
- 대입 방지: nginx `limit_req` 로 `/api/auth/login` IP 당 분당 10회(+5, 넘으면 429), backend 는 실패마다 1초 지연.
  없는 사용자와 틀린 비밀번호는 같은 응답(401 `LOGIN_FAILED`).
- **정적 화면(SPA)은 공개**. 화면 코드에는 비밀이 없고 데이터는 모두 `/api` 뒤에 있다. 화면은 `/api/me` 가 401 이면
  로그인 창(`Login.tsx` `AuthGate`), 쓰는 중 어떤 요청이든 401 이면 로그인 창으로 돌아간다.
- web 컨테이너 healthcheck 는 "정적 화면 200"(예전 "무인증 401"). `30-htpasswd.sh` 는 계정 점검(빈/견본 비밀번호면
  기동 거부)으로 남긴다 — nginx 는 그 파일을 읽지 않는다.
- 스마트폰 폭(≤760px): 메뉴 = 위쪽 가로 스크롤 줄, 카드 한 줄, 상단 알약 숨김, 드로어 전체 폭.

## 버린 것
- JWT·토큰 헤더: 화면이 요청마다 붙여야 하고 저장 위치(localStorage)가 XSS 에 약하다. 한 서버·두 계정에는 서명 쿠키면 충분.
- nginx 에서 쿠키만 비교(map): 서명 검증을 못 한다.
- 계정 DB·비밀번호 변경 화면: 계정이 `.env` 두 개뿐이라 이번엔 두지 않는다(필요해지면 이 ADR 을 바꾼다).

## 결과
- 폰(메신저 안 브라우저 포함)에서 로그인 화면이 뜬다. 스크립트·시나리오(backend 8000 직접)는 영향 없음.
- 배포 때 backend·web 을 함께 올려야 한다(web 만 새로 올리면 `/api/auth/check` 가 없어 모든 API 가 401).
- 로컬 실측(2026-09-30): 무인증 `/api/me` 401, Basic 200, 로그인 쿠키 200, 위조 `X-Remote-User` 만 401, 틀린 비밀번호 401, 연속 시도 429.
