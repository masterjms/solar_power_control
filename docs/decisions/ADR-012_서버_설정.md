# ADR-012 서버 설정 — 운영 중 화면에서 바꾸는 값, 원격 명령 응답 대기 30초 × 2회

- 날짜: 2026-10-01
- 상태: 확정 (문제점 14번 10/1 추가 요청)

## 배경
원격 명령의 무응답 판정은 `.env` 의 `COMMAND_TIMEOUT_SEC`(180초)·`COMMAND_MAX_ATTEMPTS`(3)였다. 단말측 의견:
180초는 과하다 — 응답은 30초면 온다, 반복은 2회면 충분, 최고관리자가 화면에서 바꿀 수 있어야 하고(응답 시간
10~180초 기본 30, 반복 1~3회 기본 2, 모든 단말 공통), 이런 서버 쪽 설정 항목이 계속 늘 수 있으니 따로 관리.

## 결정
### 서버 설정 = 코드의 항목 표 + DB 한 표
- 항목 정의(이름·도움말·단위·범위·기본값·묶음)는 `core/server_settings.ITEMS`. 값은 `server_setting(key, value,
  updated_by, updated_at)` — 행이 없으면 기본값. 프로세스 메모리(`runtime`)에 들고, 기동 때 읽고 저장 때 같이 바꾼다
  (백엔드는 한 프로세스). **항목 추가 = ITEMS 한 줄 + 쓰는 곳에서 `runtime.get(key)`** — API·검사·화면은 그대로.
- API `GET/PUT /api/server-settings` 는 **최고관리자 전용**(관리자 403). PUT 은 하나라도 범위 밖이면 전부 거부(422).
- 화면: 사이드바 "서버 설정"(최고관리자에게만 보임). 서버가 준 정의대로 그린다.
- `.env` 의 `COMMAND_TIMEOUT_SEC`·`COMMAND_MAX_ATTEMPTS` 는 없앴다(남아 있어도 무시).

### 원격 명령 응답 대기
- **기다리는 시간**(`command_wait_sec`, 10~180, 기본 30) × **보내는 횟수**(`command_attempts`, 처음 포함 1~3, 기본 2).
- 보낸 뒤 기다리는 시간 동안 응답이 없으면 **타이머가 같은 seq·새 ts 로 개별 topic 에 다시 보낸다**(5초 타이머,
  `claim_targets(timer=True)`). 이전에는 "단말이 뭔가 보낸 직후"에만 다시 보냈다 — 그 경로도 그대로 있고
  (최소 간격 `min(COMMAND_RETRY_MIN_SEC, 기다리는 시간)`), 둘이 같은 횟수 상한을 나눠 쓴다.
- 종료 = 기다리는 시간 × 보내는 횟수(기본 60초). 그때까지 응답 없는 대상은 `NO_RESPONSE`. 늦게 ACK 가 오면 그 결과로 바뀐다(그대로).
- 종료 판정 타이머 30초 → 5초(30초 단위 설정을 제때 지키려고).

## 서버 의견 (시트 회신)
- 30초 × 2회는 단말이 연결돼 있고 바로 받는 경우에 맞는 값이다. 사양서 §1.1.10 처럼 모뎀이 전달을 늦추는 현장
  (수십 초~수 분)에서는 60초 안에 응답이 못 와 "무응답(실패)"로 보일 수 있다 — 그때는 화면에서 기다리는 시간을 늘린다.
  늦은 응답은 결과에 반영되므로 실제 동작이 틀어지지는 않는다.
- 설정(SETTINGS)·스케줄 배포의 30초 × 3회, PING 60초는 사양서 값이라 이번 설정에 넣지 않았다. 필요하면 ITEMS 에 추가.

## 결과
- 로컬 S5-13: 10초 × 2회로 두면 무응답 단말에 약 10초 뒤 재발송(attempts 2), 23초에 `NO_RESPONSE`·`PARTIAL`.
- 시나리오는 시험 동안 180초 × 3회로 두고 끝나면 30초 × 2회로 되돌린다(docs/06).
