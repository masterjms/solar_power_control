# 2026-10-12 문제점 51번 — 관공서 진입 가능성 · AWS→온프레미스 전환 검토

결론: **기술 구조로는 진입 가능**하다(단말↔서버 암호화, 단말별 계정, 역할·지역 권한, 접속 기록이 이미 있다).
다만 공공 발주에서 흔히 요구하는 항목 중 **계정 보안 세부 규칙, 보안 점검 결과서, 망분리 환경의 외부 서비스 대체, 성능 시험 결과**가 비어 있다.
정확한 요구는 기관마다 다르므로, **첫 대상 기관의 제안요청서(RFP)·시방서 보안 요건을 받아 아래 표와 맞춰 보는 것**이 첫 단계다.

## 1. 지금 갖춘 것

| 영역 | 현재 |
|---|---|
| 단말↔서버 | MQTT over TLS 1.2(8883), RSA 2048 공인 인증서, 단말마다 다른 접속 계정(서버 키로 만든 비밀번호), 단말은 자기 주소만 읽고 쓰기(ACL) |
| 관제 화면 | HTTPS, 비밀번호 PBKDF2 저장, 역할 3단계(최고관리자·지역관리자·게스트) + 지역 범위, 사용 기간·사용 중지 |
| 기록 | 로그인 기록(성공·실패·IP) 1년, 원격 명령 "누가·언제·무엇", 설정 변경 이력, 단말 이벤트, 엑셀 내보내기 |
| 운영 | 매일 DB 백업(7일)+디스크 스냅샷, 서버 다운 알림, 자동 재시작, 인증서 자동 갱신 |
| 데이터 | 개인정보는 관제 계정(아이디·접속 IP)뿐. 단말 데이터는 공공 시설 운전 값 |

## 2. 관공서 진입에 필요한 것 (기능 · 보안 · 성능)

### 2.1 클라우드를 쓸 경우
- 공공기관이 민간 클라우드를 쓰려면 **CSAP(클라우드 보안인증)** 받은 서비스여야 한다. AWS 서울 리전은 2025-04 **'하' 등급**을 받았다(개인정보가 없는 공개 데이터 시스템용).
- 이 시스템은 개인정보가 관제 계정 정도라 '하' 등급 범주로 볼 여지가 있으나 **판단은 기관 몫**이다. 기관이 '중' 이상을 요구하면 국내 CSP(중·상 등급 보유사) 또는 온프레미스로 가야 한다.

### 2.2 보안 — 보완 필요(서버 개발)
| 항목 | 흔한 요구 | 지금 | 할 일 | 규모 |
|---|---|---|---|---|
| 비밀번호 규칙 | 9자 이상·문자 종류 조합, 주기 변경 | 8자 이상만 | 규칙·변경 주기 알림 | 1일 |
| 로그인 실패 잠금 | 5회 실패 시 잠금 | 1초 지연 + 요청 수 제한 | 계정 잠금·해제(최고관리자) | 1일 |
| 세션 | 무동작 10~30분 자동 로그아웃 | 7일 유지 | 무동작 시간 설정(서버 설정 화면) | 0.5일 |
| 관리자 2단계 인증 | 최고관리자 OTP 등 | 없음 | OTP(앱) 선택 적용 | 2~3일 |
| 감사 기록 | 조작 이력 위·변조 방지, 1년 이상 | 이력은 있음, 화면 조회 위주 | 감사 기록 화면·내보내기, 삭제 금지 | 1~2일 |
| 보안 점검 | 소프트웨어 보안약점 진단(시큐어코딩), 웹 취약점 점검 결과서 | 내부 점검만 | 외부 진단 1회 + 지적 사항 수정 | 진단 기관 일정 |
| 암호모듈 | 기관에 따라 **검증필 암호모듈(KCMVP)** 요구 | OpenSSL(검증필 아님) | 요구 시 검증 모듈로 교체(서버·단말 모두 영향) — RFP 확인 우선 | 큼 |
| 단말 인증 | IoT 보안인증(KISA) 등 가점·요건 | — | 단말측 검토 | 단말 |

### 2.3 망분리 환경 — 외부 서비스 대체
관제 PC가 기관 업무망(인터넷 차단)이면 지금 쓰는 외부 서비스가 막힌다.
| 지금 | 막히면 | 대체 |
|---|---|---|
| 카카오 지도·주소 검색 | 지도 안 뜸, 주소 검색 안 됨 | 공공 지도(브이월드 등) 또는 기관 지도, 주소는 도로명주소 API/내부 DB |
| Slack 알림 | 알림 안 감 | 기관 메일·문자(SMS) 게이트웨이 |
| UptimeRobot(외부 감시) | — | 내부 감시(서버 자체 점검 + 메일/문자) |
| Let's Encrypt 인증서 | 자동 발급 안 됨(외부 확인 필요) | 기관 지정 인증서 — **단말 CA 파일도 바뀜(아래 3.3)** |

### 2.4 성능
- 설계는 1만 대·1년 보관. 로컬 PC 시험은 300대 폭주까지. **운영 사양에서 1만 대 가상 단말 시험 결과서**를 한 번 만들어 두면 제안·검수 때 쓴다(가상 단말 도구는 있음, 약 2일).

## 3. AWS → 온프레미스 전환

### 3.1 하드웨어(1만 대, 보고 10분 주기, 1년 보관 기준)
- 보고 1일 약 144만 줄 → 1년 약 5억 줄, DB 약 300~400GB(색인 포함). 보관 개월은 서버 설정에서 줄일 수 있다.
| 구성 | 권장 |
|---|---|
| 서버 | 2대(운영 + 대기/복구) — 각 CPU 8코어, 메모리 32GB, SSD 2TB(RAID 1) |
| 최소 | 1대 — 8코어, 16GB, SSD 1TB (장애 시 복구 시간 길어짐) |
| 백업 | NAS 또는 별도 디스크(매일 DB 백업 30일 이상) |
| 기타 | UPS, 고정 공인 IP, 도메인, 시간 동기(NTP) |
| OS | Ubuntu 22.04/24.04 LTS (기관이 다른 리눅스를 요구하면 확인) |

### 3.2 네트워크
- 단말은 LTE(통신사 망)로 들어온다. 서버를 기관 안에 두면 **DMZ에 단말 통신 서버(8883)를 두고 방화벽 허용**이 필요하다(기관 보안 심의).
- 인터넷 노출을 없애려면 **통신사 전용망(사설 APN)** 구성 — 비용·통신사 협의 필요, 단말 설정 변경.

### 3.3 인증서 — 단말에 영향
- 단말은 지금 **ISRG Root X1(Let's Encrypt 최상위)만 믿는다**. 기관이 다른 인증서(상용 CA·기관 인증서)를 쓰면 **단말의 CA 파일을 바꿔야** 한다 → 현장 단말 원격 갱신 방법(단말측) 확인 필요.

### 3.4 개발·준비할 것 (서버, 약 2~4주)
1. 설치 스크립트를 AWS 전용(EC2·SSM·스냅샷)에서 일반 서버용으로 — 화면·서버는 Docker 그대로 옮겨진다.
2. 백업을 NAS로, 복구 연습 절차서.
3. 알림을 메일·문자로(Slack 대체), 내부 감시.
4. 지도·주소 검색 대체(망분리 시).
5. 2.2 보안 보완 항목.
6. 운영 설명서(설치·백업·복구·인증서·장애 대응).

## 4. 제안 순서
1. 첫 대상 기관의 RFP·시방서 보안 요건 확보 → 이 표와 차이 정리(1일).
2. 계정 보안 보완(비밀번호·잠금·세션·감사, 약 3~4일) — 클라우드·온프레미스 어디든 필요.
3. 1만 대 성능 시험 결과서(약 2일).
4. 외부 보안 진단(기관 지정 또는 전문 업체).
5. 온프레미스면 3장 준비(HW 발주와 병행).
